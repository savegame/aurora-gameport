# Разведка рендер-пайплайна движка

Этот документ читай на **этапе 0** (начальное исследование проекта) —
до любых изменений кода. Чеклист ниже заполняется один раз; полный
отчёт пишется в `research/render_pipeline.md`, дайджест — в
`port_status.md` (раздел «Дайджест разведки»). В дальнейших сессиях
читай дайджест в `port_status.md`, а полный отчёт — только если
дайджеста не хватает. Раздел «Опасные
места» актуален и позже — на этапах 2–3 (интеграция FBO, поворот).

До любых изменений кода исследуй движок и зафиксируй ответы
в `research/render_pipeline.md`. Ничего не меняй, пока разведка
не завершена.

## Чеклист разведки

1. Какой графический API использует движок. Совместим ли он с GLES3.
   Если проект рендерит только через чистый OpenGL — стоп, эскалация
   пользователю. По решению пользователя открывается этап
   «Мобильный рендер» — исследование по `docs/GLES3_Render_Research_Plan.md`
   (см. «Поэтапный план» в AGENTS.MD).
2. Как устроен рендер-пайплайн до вызова swap. Найди вызов swap:
   glSwapBuffers, SDL_GL_SwapWindow, irrlicht endScene или аналог —
   определи, какой именно используется в этом движке.
3. Куда рисуется игровая сцена: напрямую в бэкбуфер (direct draw)
   или движок уже рендерит в своё FBO и затем swap. Движковое FBO
   НЕ переиспользуем и НЕ модифицируем: мы подменяем только прямой
   вывод на экран (бинд бэкбуфера), более ничего. Для движка наш FBO
   выглядит как экран: он по-прежнему отрисовывает своё 3D-FBO,
   а затем свой UI — уже в наш FBO, как если бы рисовал напрямую
   на экран.
4. Как движок выставляет буфер рендеринга. На чистом GLES ищи
   glBindFramebuffer(GL_FRAMEBUFFER, 0) — бинд 0 означает рендер
   в бэкбуфер (на экран). Все такие места — кандидаты на замену
   бинда 0 биндом нашего FBO.
5. Как движок узнаёт размер окна/экрана: глобальная переменная,
   запрос через SDL2 API, другой путь. Важно: размер ОКНА и размер
   ЭКРАНА (дисплея) — разные вызовы API, движок может дёргать оба
   (например, SDL_GetWindowSize и SDL_GetDisplayBounds/
   SDL_GetCurrentDisplayMode) — найди все такие места, иначе часть
   подмен будет пропущена. Сюда позже внедряется подмена размера
   закешированным размером нашего FBO.
6. Сколько путей вывода графики у движка. Обычно swap один за кадр,
   но возможны раздельные режимы (меню / игра) с разными путями
   вывода — найди все.
7. Использует ли движок собственный API для render target. Приоритет
   выбора средств: сначала существующий API движка — так меньше шанса
   навредить, — но только если его вызов не переусложняет кросс-
   зависимости между модулями. Иначе — чистый GLES3, если это легко
   и уместно.
8. Где движок забирает события ввода (мышь/тач): SDL_PollEvent,
   GLFW-колбэки, свой слой абстракции. Это кандидат на точку
   перехвата для трансформации координат (см. «Этап 4.
   Трансформация ввода» в AGENTS.MD).
9. Где и как движок кэширует GL-состояние (call bridge, dirty-флаги,
   свои обёртки над gl-вызовами). Зафиксируй, что FBO-модуль обязан
   восстановить после вывода квада и как (через API движка или
   возвратом значений из кэша — см. «Опасные места» ниже). Пропуск
   этого пункта дорого обходится в отладке: рассинхрон кэша (например,
   viewport) даёт дефект рендера, который по симптомам похож на
   ошибку в размерах или маппинге transform.

## Опасные места

- Состояние GL: при отрисовке нашего буфера мы выставляем свои
  glProgram. Убедись, что рендер движка не сломается: движок ожидает
  свои шейдеры. На практике большинство движков дёргают glUseProgram
  перед отрисовкой геометрии — тогда конфликта нет. Проверить
  обязательно.
- Кэшированное GL-состояние движка. Движок может кэшировать GL-state
  и пропускать «лишние» gl-вызовы (например, в irrlicht —
  COGLES2CallBridge кэширует viewport и др.). Если FBO-модуль меняет
  состояние сырыми gl-вызовами мимо этого кэша, кэш расходится с
  реальным состоянием: на следующих кадрах движок считает его уже
  выставленным и не перевыставляет — дефект живёт, пока значение не
  сменится через API движка. Правила:
  - При создании FBO-модуля сначала ищи движковые API для тех
    GL-операций, которые нужны модулю (viewport, биндинги
    framebuffer/текстур, флаги состояния), и используй их вместо
    сырых вызовов GLES3 — тогда кэш движка остаётся согласованным
    сам (пример: в порту RE3 для этого использовался API librw
    вместо сырого GLES3). Это заметно снижает риск рассинхрона.
  - Если движкового API нет и без сырых вызовов не обойтись — всё,
    что модуль трогает при выводе квада (glViewport, биндинги
    framebuffer/текстур/VAO, флаги depth/stencil/blend/scissor/cull),
    восстанавливай после блита, возвращая значения из кэша движка.
  - Не вычитывай состояние через glGet* каждый кадр — это дорого
    и не нужно: смотри, как состояние кэшируется в движке, и бери
    значения оттуда.
  Прецедент (порт STK): движок кэшировал glViewport, а FBO-модуль
  при выводе квада выставлял viewport сырым gl-вызовом мимо кэша
  и не восстанавливал его. На следующем кадре движок считал свой
  viewport уже активным и рисовал не в тот viewport: на экране —
  часть кадра, растянутая и смещённая, при этом все читаемые через
  API размеры были правильными — отладка сначала шла по ложному
  следу (размеры, маппинг transform).
- Маппинг «ориентация → buffer transform», зашитый под один тип
  панели: на портретной панели landscape = 90°, на ландшафтной = 0°
  (см. таблицу в «Маппинг ориентаций под ориентацию игры» в
  `docs/fbo_module.md`). Если захардкодить 90/270, рендер ломается
  на ландшафтных панелях и при переносе окна на внешний монитор.
  Тип панели определяй по нативному разрешению текущего дисплея,
  но пересчитывай его ОДИН раз при инициализации и далее только
  при смене дисплея (перенос окна на другой output) — по событию
  смены дисплея фреймворка, если оно есть (у SDL2 и GLFW3 такие
  события/API есть). Не пересчитывай тип панели на каждый поворот
  и тем более на каждый кадр: нативные размеры дисплея фреймворк
  сам кэширует при получении mode от композитора, частые запросы
  ничего не дают.
- Асимметрия канонизации путей при симлинковом дереве ресурсов:
  при установке пакета на Авроре создаются симлинки на все файлы
  пакета, и приложение в рантайме работает уже с симлинками — со
  всеми ресурсами, библиотеками и контентом, установленными в
  `/usr/share/org.example.appname/*` (реальные файлы лежат отдельно,
  например в `/opt/app/<name>`). Если одна часть движка канонизирует
  путь (realpath), а другая сравнивает с ним текстовый путь,
  строковое сравнение промахивается: ресурс (материал, текстура,
  модель) не находится и молча подставляется дефолтный — без ошибок
  в логе. Правило: либо канонизируй пути во всех лоадерах
  симметрично, либо нигде; любые строковые сравнения путей — только
  после одинаковой канонизации обеих сторон.
