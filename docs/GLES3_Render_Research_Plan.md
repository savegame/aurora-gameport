# План исследования рендера: переход desktop OpenGL → GLES3

> Методический документ к условному этапу «Мобильный рендер» из AGENTS.md.
> Выполняется только по решению пользователя после этапа 0, когда выяснилось,
> что проект рендерит только через desktop OpenGL и с GLES3/Vulkan напрямую
> не совместим.
>
> Вход: результаты этапа 0 и чеклиста разведки
> (`docs/render_pipeline_research.md`), зафиксированные в
> `research/render_pipeline.md`.
> Выход: документ `research/Research_Render_Report.md` (шаблон — в
> конце этого документа) и согласованный с пользователем план

> и стратегия не утверждена пользователем.

## 1. Принципы выбора стратегии

Исследование всегда ведёт к выбору одной из стратегий (раздел 5). Приоритеты,
по которым стратегии сравниваются:

1. **Чистый GLES3-рендер — в приоритете.** GLES3 поддерживается всеми
   целевыми устройствами, Vulkan — большинством (см. AGENTS.md, этап
   «Мобильный рендер»). Стратегии на базе Vulkan-мостов рассматриваются
   только когда чистый порт и gl4es неприменимы или несоизмеримо дороже.
2. **Минимум вторжения.** Изменения только в слое рендера и платформенной
   интеграции; логику игры не менять (правило AGENTS.md сохраняется).
3. **Изоляция порта дефайном.** Весь код GLES3-порта закрывается дефайном
   (имя — по стилю дефайнов движка). Сборка без дефайна = движок работает
   ровно как раньше.
4. **Отключение, а не переписывание эффектов.** Если движок умеет штатно
   отключать эффекты/фичи (настройки, конфиг, консольные команды, дефайны),
   несовместимые с GLES3 эффекты в GLES3-сборке отключаются по умолчанию
   (формализация — раздел 3.3). Их переписывание под GLES3 — отдельная
   задача, только по решению пользователя.
5. **Библиотеки-мосты — легитимный путь, а не «костыль последней надежды».**
   gl4es для GL 1.x/2.x-проектов часто даёт рабочий порт за дни вместо
   месяцев. Цена — производительность и ограничения покрытия; обе величины
   измеряются в ходе исследования, а не предполагаются.
6. **Не смешивать стратегии** в одном бинаре без явной необходимости.

### Важное терминологическое уточнение

- **gl4es** — транслятор OpenGL 1.5/2.1 → GLES 1.1/2.0 (бэкенд GLES3
  существует, но моложе). Подходит для fixed pipeline и старых GL2-шейдеров.
- **Zink (Mesa)** — реализация desktop OpenGL (вплоть до 4.6, конформантно)
  поверх Vulkan. Это и есть «OpenGL через Vulkan».
- **ANGLE (Google)** — реализация OpenGL ES 2.0–3.1 (3.2 — по Vulkan-бэкенду)
  поверх Vulkan/D3D/Metal/desktop GL. ANGLE НЕ исполняет desktop OpenGL-код:
  это слой GLES→Vulkan. Его роль в нашем процессе — запасной GLES-драйвер
  для устройств с глючным штатным GLES и удобный полигон для отладки
  GLES3-порта на десктопе без устройства.

## 2. Шаг 1. Инвентаризация графического API проекта

Цель шага — однозначно классифицировать профиль GL проекта и получить полный
список используемых вызовов, расширений и шейдеров. Результаты фиксируются
в `Research_Render_Report.md` (раздел «Профиль GL проекта»).

### 2.1. Классификация профиля GL

Определи, к какому классу относится рендер движка. Маркеры для поиска
(grep по исходникам):

| Класс | Маркеры |
|---|---|
| Fixed pipeline (GL 1.x) | `glBegin`, `glEnd`, `glMatrixMode`, `glLoadIdentity`, `glLight`, `glMaterial`, `glEnable(GL_LIGHTING)`, `glTexEnv` |
| GL 1.x с VBO/массивами | `glVertexPointer`, `glNormalPointer`, `glTexCoordPointer`, `glDrawArrays` без `glUseProgram` |
| GL 2.x (шейдеры, compatibility) | `glUseProgram`, `glVertexAttribPointer`, GLSL `#version 110/120`, `texture2D`, `attribute`/`varying` |
| GL 3.x core | `glGenVertexArrays`, GLSL `#version 330`, `in`/`out`, `texture()`, UBO `glUniformBuffer` |
| GL 4.x | `glDispatchCompute`, `GL_TESS_CONTROL_SHADER`, `GL_GEOMETRY_SHADER`, `glShaderStorageBuffer`, `#version 4xx` |

Проект может смешивать классы (типично: современный рендер + legacy UI на
fixed pipeline). Классифицируй по самому тяжёлому используемому классу,
но фиксируй все обнаруженные.

### 2.2. Полный реестр GL-вызовов

Извлеки все уникальные GL-вызовы проекта, например:

```sh
grep -rhoE '\bgl[A-Z][A-Za-z0-9]+' --include='*.c' --include='*.cpp' --include='*.h' --include='*.hpp' . \
  | sort | uniq -c | sort -rn
```

Для каждого вызова заполни колонку совместимости:

- **core GLES3** — есть в GLES3 без изменений;
- **изменён** — есть, но с другой сигнатурой/семантикой (например,
  `glTexImage2D` с desktop-only internal format, `glClearDepth` →
  `glClearDepthf`);
- **расширение** — нет в core, но существует `OES_*`/`EXT_*`/`KHR_*` аналог
  (указать какой);
- **нет** — отсутствует в GLES принципиально (`glBegin`, `glPolygonMode`,
  `glDrawPixels`, `glClipPlane`);
- **версия ES** — есть, начиная с конкретной версии ES: compute-шейдеры
  и SSBO (`glDispatchCompute`, `glShaderStorageBuffer`) — ES 3.1;
  geometry/tessellation-шейдеры — ES 3.2. Совместимость таких вызовов
  определяется выбранным целевым профилем (шаг 3.6).

### 2.3. Реестр расширений

Найди все места, где движок проверяет расширения (`glGetString(GL_EXTENSIONS)`,
`glewIsSupported`, `glfwExtensionSupported`, макросы `GL_ARB_*`/`GL_EXT_*`
в `#ifdef`). Составь таблицу:

| Расширение GL | Где используется | Аналог в GLES3 (core / EXT / OES) | Действие |
|---|---|---|---|

Типовые соответствия: `GL_ARB_framebuffer_object` → core ES3;
`GL_EXT_texture_compression_s3tc` → нет на большинстве мобильных GPU
(там ETC2/ASTC — core ES3 / `KHR_texture_compression_astc_ldr`);
`GL_ARB_instanced_arrays` → core ES3; `GL_ARB_occlusion_query` → core ES3;
`GL_EXT_texture_format_BGRA8888` → существует и на ES (проверять на
устройстве).

### 2.4. Реестр шейдеров

Инвентаризируй ВСЕ шейдеры: и файлы (`.glsl`, `.vert`, `.frag`, `.shader`
и т.п.), и **шейдеры, собираемые строками в коде** (конкатенация, генерация
— их легко пропустить, ищи по `glShaderSource` и просматривай источники
строк). Для каждого шейдера: `#version`, используемые конструкции
(`texture2D`/`textureCube`, `attribute`/`varying`, `gl_FragColor`,
`texture2DLod`, массивы семплеров и т.п.).

Отдельно проверь: не генерирует ли движок fixed-pipeline-эквивалент
шейдеров сам (некоторые движки эмулируют FFP шейдерами — тогда порт может
оказаться проще, чем кажется по количеству `glBegin`).

### 2.5. Загрузчик GL-функций

Найди, чем проект грузит entry points: GLEW, glad (какой генерации),
gl3w, SDL_GL_GetProcAddress, самописный. Это точка переключения:
- GLEW корректно не работает с ES-контекстом → замена на glad2
  (профиль `gles2`, core 3.0) либо прямая линковка с `libGLESv2` +
  `eglGetProcAddress`;
- SDL_GL_GetProcAddress и самописные лоадеры обычно достаточно направить
  на ES-заголовки.

### 2.6. Создание контекста

Найди, как создаётся GL-контекст и с какими атрибутами:
- SDL2: `SDL_GL_SetAttribute(SDL_GL_CONTEXT_PROFILE_MASK, ...)`,
  `SDL_GL_CONTEXT_MAJOR/MINOR_VERSION`;
- GLFW: `glfwWindowHint(GLFW_CLIENT_API / GLFW_CONTEXT_VERSION_*)`;
- собственный EGL-код: `eglChooseConfig`, `eglBindAPI`.

Зафиксируй текущие атрибуты — они определяют, какой профиль запрашивает
движок (compatibility/core), и где переключать на ES:
`SDL_GL_CONTEXT_PROFILE_ES` + версия 3.0; GLFW: `GLFW_OPENGL_ES_API`;
EGL: `EGL_OPENGL_ES3_BIT`.

### 2.7. Итог шага 1

Одна строка-классификация (например: «GL 2.1 compatibility + fixed-pipeline
UI, GLSL 1.20, 47 уникальных вызовов, из них 12 несовместимы, 3 расширения
без ES-аналога») + заполненные таблицы 2.2–2.4. Эта строка — главный
вход для матрицы выбора стратегии (раздел 5).

## 3. Шаг 2. Аудит эффектов и фич движка

### 3.1. Реестр визуальных фич

Составь реестр рендер-фич движка: HDR, bloom, SSAO, тени (shadow maps,
PCF, CSM), отражения, преломления, MSAA, post-processing-цепочки, частицы
(CPU/GPU), occlusion culling, instancing, скиннинг на GPU, декали, volumetric
effects, motion blur и т.п. Источники: настройки графики в меню/конфиге,
классы материалов/эффектов, имена файлов шейдеров.

### 3.2. Таблица совместимости фич

Для каждой фичи:

| Фича | GL-механизм | Совместимость с GLES3 | Есть штатное отключение? | Действие |
|---|---|---|---|---|
| пример: MSAA 4x | multisample renderbuffer | исключён спекой (без MSAA) | да, настройка | отключить по умолчанию |
| пример: HDR bloom | float FBO RGBA16F | через `EXT_color_buffer_float` (проверить на устройстве) | да | оставить с runtime-проверкой, fallback — отключить |
| пример: occlusion culling | `GL_SAMPLES_PASSED` | core ES3 | — | оставить |
| пример: clip planes | `glClipPlane` | нет в ES3 | нет | переписать (шейдерный discard / `EXT_clip_cull_distance`) или отключить эффект |

Колонка «Действие» принимает одно из четырёх значений:
- **оставить** — фича совместима (core или надёжное расширение);
- **оставить с runtime-проверкой** — зависит от расширения/лимита, на
  устройстве проверяем и при отсутствии отключаем;
- **отключить по умолчанию** — несовместима, но движок умеет её выключать;
- **переписать** — несовместима и неотключаема штатно (кандидат на
  ручной порт; только с оценкой трудоёмкости).

### 3.3. Правило отключения эффектов по умолчанию (формализация)

Если фича несовместима с GLES3 И движок предоставляет штатный способ её
отключить (настройка, конфиг-файл, консольная команда, дефайн сборки), то
в GLES3-сборке:

1. Фича **выключается по умолчанию** — через тот же штатный механизм
   (дефолт конфига под дефайном порта, принудительный clamp значения
   настройки, compile-time исключение — в порядке предпочтения: сначала
   дефолт конфига, затем clamp, затем дефайн).
2. Факт отключения **логируется** при старте (одна строка на фичу:
   «эффект X отключён: несовместим с GLES3»).
3. Ручка включения в UI/конфиге **блокируется или помечается
   экспериментальной**, чтобы пользователь не включил заведомо сломанное.
   Способ — на усмотрение по стилю движка, но под тем же дефайном порта.
4. Возврат фичи (переписывание под GLES3) — отдельная задача за рамками
   первой итерации, открывается только по решению пользователя.

### 3.4. Справочная таблица типовых несовместимостей desktop GL → GLES3

Проверяй проект по этому списку даже если вызовы не нашлись grep'ом —
они могут быть скрыты в библиотеках/мидлваре движка:

- `GL_QUADS` / `GL_QUAD_STRIP` — нет в ES: конвертация в треугольники
  (в UI-коде встречается чаще всего);
- `glPolygonMode(GL_LINE)` — в ES только `GL_FILL` (wireframe-режимы отладки
  отключаются);
- `glDrawPixels`, `glBitmap`, `glCopyPixels` — нет в ES: заменяются
  текстурированным квадом / `glBlitFramebuffer`;
- fixed pipeline целиком (`glBegin/glEnd`, матричный стек, освещение,
  `glTexEnv`) — нет в ES3;
- compute-шейдеры и SSBO — ES 3.1, geometry/tessellation-шейдеры —
  ES 3.2: допустимы, если целевой профиль поднят до соответствующей
  версии (шаг 3.6); при профиле 3.0 эффекты на них — отключать
  по умолчанию;
- `gl_ClipDistance` в шейдерах — только через `EXT_clip_cull_distance`;
- `texture2DLod`/`textureLod` вне вершинного шейдера — в ES3 есть
  `textureLod` core, но в GLSL 1.20-портированных шейдерах проверять;
- internal formats: `GL_BGRA`, `GL_RGB` без sized-формата, `GL_ALPHA`/
  `GL_LUMINANCE` (в ES3 deprecated) — приводить к sized-форматам ES3;
- float render targets: рендер в RGBA16F/RGBA32F — через
  `EXT_color_buffer_float` / `EXT_color_buffer_half_float` (проверять на
  устройстве, иначе эффект — на отключение);
- MRT: минимум 4 attachment гарантирован, больше — по
  `GL_MAX_COLOR_ATTACHMENTS`;
- ширина линий > 1 и размер точек — лимиты сильно уже desktop;
- compressed textures: S3TC на мобильных обычно нет — нужны ETC2/ASTC-варианты
  ассетов или распаковка на CPU;
- `GL_DEPTH24_STENCIL8` — есть в ES3 (совмещённый depth+stencil, см.
  требования к FBO-модулю в AGENTS.md);
- MSAA — исключён спекой в любом случае; эффекты, завязанные на MSAA,
  отключаются или переводятся на имеющуюся у движка альтернативу
  (FXAA и т.п.), если она есть.

### 3.5. Лимиты целевого устройства

На первом же запуске тестового бинаря на устройстве сними и приложи к отчёту
дамп: `GL_VERSION`, `GL_RENDERER`, `GL_SHADING_LANGUAGE_VERSION`,
`GL_EXTENSIONS`, `GL_MAX_TEXTURE_SIZE`, `GL_MAX_VERTEX_ATTRIBS`,
`GL_MAX_TEXTURE_IMAGE_UNITS`, `GL_MAX_COLOR_ATTACHMENTS`,
`GL_MAX_FRAGMENT_UNIFORM_VECTORS`, наличие `EXT_color_buffer_float`,
`EXT_texture_format_BGRA8888`, `KHR_debug`. Версия ES из `GL_VERSION` — подтверждение выбранного
целевого профиля (шаг 3.6). Это база для всех решений
«оставить с runtime-проверкой».

### 3.6. Выбор целевого профиля ES

По итогам аудита зафиксируй в отчёте целевой профиль: 3.0 / 3.1 / 3.2.
Правило выбора:
- **3.0** — базовый, если проекту хватает его возможностей;
- **3.1** — если нужны compute-шейдеры/SSBO (поддержка на устройствах
  повсеместная);
- **3.2** — если нужны geometry/tessellation-шейдеры (поддерживается
  практически всеми актуальными устройствами, но обязательно подтверди
  дампом `GL_VERSION` на целевых устройствах).

Поднятие профиля сужает парк устройств — решение принимается осознанно
и фиксируется в отчёте одной строкой с обоснованием. Выбранный профиль
наследуется всеми остальными шагами: классификация вызовов (2.2),
решения по эффектам (3.2), контекст (4), конверсия шейдеров (ESSL
300 es / 310 es / 320 es), милистоуны (7).

## 4. Шаг 3. Карта интеграции и оценка объёма

1. **Карта модулей рендера.** Определи, в каких файлах/классах сосредоточен
   GL-код, и есть ли у движка слой абстракции рендера (render driver /
   backend / video module с несколькими реализациями). Если абстракция
   есть — объём работ резко ниже: новый бэкенд вместо правок по всему коду.
2. **Проверка существующих бэкендов.** Выясни, нет ли у движка уже
   GLES2/GLES3- или Vulkan-рендера: в самом коде (неактивный дефайн,
   недописанный модуль), в апстрим-ветках, в форках. **Обязательно поищи
   Android-порты проекта и движка** — в них обычно уже решена бо́льшая
   часть GLES-адаптации (шейдеры, загрузчик, контекст), и это самый
   дешёвый источник готовых решений.
3. **Точки переключения.** Зафиксируй конкретные места: создание контекста
   (2.6), загрузчик (2.5), шейдерный компилятор движка (где внедрять
   конвертацию/препроцессинг шейдеров), все бинды бэкбуфера
   (`glBindFramebuffer(GL_FRAMEBUFFER, 0)` — пересечение с разведкой
   AGENTS.md пп. 2–7).
4. **Грубая оценка трудоёмкости** чистого порта по счётчикам:
   - S (дни): абстракция рендера есть, вызовов «нет» ≤ 10, шейдеров ≤ 20,
     fixed pipeline нет;
   - M (недели): абстракции нет, но GL-код компактный; «нет» ≤ 30;
     fixed pipeline только в UI;
   - L (месяц+): «нет» > 30 или fixed pipeline в основном рендере,
     шейдеров > 50, генерируемые шейдеры;
   - XL: GL 4.x-фичи в ядре рендера (compute/tessellation/geometry),
     эффекты на них неотключаемы — чистый порт почти наверняка
     неоправдан, смотри матрицу.

## 5. Шаг 4. Выбор стратегии — матрица решений

### Стратегии

**S1. Чистый порт на GLES3** (приоритетная).
Замена несовместимых вызовов, конвертация шейдеров в ESSL 300 es /
310 es / 320 es (по выбранному профилю, шаг 3.6), переключение контекста
и загрузчика на ES, отключение эффектов по таблице 3.2. Под дефайном
порта. Плюсы: нативная производительность,
нет лишних зависимостей, максимум контроля. Минусы: самый дорогой путь
при тяжёлом профиле GL.

**S2. gl4es** (OpenGL 1.5/2.1 → GLES 1.1/2.0, бэкенд GLES3 моложе).
Библиотека линкуется вместо libGL и транслирует вызовы, включая
immediate mode и часть display lists; GLSL 1.20-шейдеры транслируются
в ESSL. Плюсы: рабочий порт fixed-pipeline/GL2-проектов за малое время;
проверена на десятках портированных игр; MIT. Минусы: оверхед трансляции
(критично для тяжёлых сцен), покрытие неполное, GLSL-трансляция имеет
пределы, для GL 3.x core-проектов не подходит. Интеграция: сборка
CMake под оба таргета, линковка вместо системного GL, установка .so
в `/usr/share/%{name}/lib` + patchelf + `__requires_exclude` (см. AGENTS.md,
«Сборка пакета»). Для конкретных игр существуют специализированные форки
gl4es — поищи форк под этот проект/движок.

**S3. Zink (Mesa): desktop OpenGL поверх Vulkan.**
Единственный путь «не трогать GL-код вообще» для проектов на GL 3.3+/4.x.
Условия применимости: (а) на целевых устройствах есть рабочий
Vulkan-драйвер с фичами из профиля Zink — по AGENTS.md Vulkan есть
«на большинстве» устройств, значит стратегия не универсальна и требует
проверки на каждом целевом устройстве; (б) сборка Mesa (gallium + zink +
vulkan loader) тулчейном под aarch64/armv7hl — тяжёлая отдельная цепочка;
(в) заметный рост размера пакета; (г) работоспособность wayland-egl пути
проверяется прототипом. Плюсы: покрытие GL 4.6 конформантно. Минусы:
самая тяжёлая сборочная и упаковочная интеграция, зависимость от качества
Vulkan-драйвера устройства, оверхед слоя.

**S4. ANGLE (GLES 2.0–3.1 поверх Vulkan).**
НЕ решает задачу запуска desktop GL. Роли в нашем процессе:
(а) полигон для разработки/отладки чистого GLES3-порта (S1) на десктопе —
конформантный ES-контекст без устройства; (б) запасной GLES-драйвер на
устройствах, где штатный GLES глючен, но есть Vulkan. Оговорка: система
сборки ANGLE тяжёлая (depot_tools/gn/ninja, большой чекаут) — встраивание
в RPM-сборку нетривиально; рассматривать как (б) только после успешного S1
и при подтверждённых проблемах драйверов.

**S5. Существующий мобильный/Vulkan-бэкенд движка или форка.**
Если шаг 4.2 нашёл готовый GLES3/Vulkan-рендер (в апстриме, ветке, форке,
Android-порте) — это почти всегда дешевле любой из S1–S4: задача сводится
к переносу бэкенда и адаптации платформенного слоя.

### Матрица выбора

| Профиль проекта (итог шага 1) | Рекомендуемый порядок |
|---|---|
| Fixed pipeline / GL 1.x–2.1, immediate mode | S5 → **S2 (gl4es)** → S1 (переписывание UI + рендера) |
| GL 2.x с шейдерами, compatibility | S5 → **S1** → S2 |
| GL 3.x core, умеренный объём, абстракция есть | S5 → **S1** (типично S/M по оценке) |
| GL 3.x/4.x, тяжёлый, фичи GL4 неотключаемы | S5 → **S3 (Zink)** с обязательной проверкой Vulkan на целевых устройствах → S1 с отключением максимума эффектов |
| GLES3-порт сделан, на части устройств глючит драйвер | **S4 (ANGLE)** как запасной драйвер |

В матрице S5 стоит первой всегда: готовый бэкенд дешевле любого порта.

### Сравнение при выборе — критерии

Для отчёта сравни применимые стратегии по: трудоёмкости (оценка шага 4.4),
производительности (оверхед слоя трансляции), покрытию устройств
(GLES3 — все; Vulkan-мосты — меньше), поддерживаемости (сложность мерджа
с апстримом: чистый порт сложнее мерджить, мост — легче), размеру пакета,
лицензиям (gl4es — MIT, ANGLE — BSD-3, Zink/Mesa — MIT: все совместимы,
но тексты лицензий включить в пакет), риску для основной ветки движка
(при дефайн-изоляции — низкий у всех).

## 6. Шаг 5. Прототип и верификация гипотез

До финализации плана реализации проведи дешёвую проверку ключевой гипотезы:

1. **Десктопный прогон под ES3.** На Linux ES3-контекст дают Mesa
   (профиль ES через SDL2/GLFW) и ANGLE. Попробуй собрать проект с
   ES-заголовками и ES-контекстом на десктопе: список ошибок компиляции
   и рантайма — лучшая валидация оценки объёма из шага 4.
2. **apitrace.** Сними трассу desktop-версии (`apitrace trace`): реальный
   поток вызовов, состояния, FBO-операции. После порта снимай трассы
   GLES-версии для сравнения кадр в кадр.
3. **RenderDoc** (на Linux с ES поддерживает захват) — покадровый разбор
   при визуальных расхождениях.
4. **glslangValidator** — валидация сконвертированных шейдеров под
   ESSL 3.00 (`glslangValidator --target-env opengl` / проверка синтаксиса
   `#version 300 es`). Оговорка: надёжного универсального авто-конвертера
   GLSL→ESSL не существует; конверсия идёт вручную или через
   препроцессорные шаблоны движка (подмена `#version`, инжект
   `precision`-квалификаторов, маппинг `texture2D`→`texture`,
   `attribute/varying`→`in/out`, `gl_FragColor`→свой `out`).
5. **Дамп лимитов на устройстве** (шаг 3.5) — первый device-прогон.

Критерий завершения прототипа: выбранная стратегия показала базовый рендер
(хотя бы очистка цветом + простейшая сцена/меню) на десктопе под ES3 или
на устройстве. Если гипотеза не подтвердилась — возврат к матрице
стратегий с новыми данными, итерацию фиксируй в отчёте.

## 7. Шаг 6. Формализация плана реализации

Результат исследования — план реализации со строго такой структурой
(входит в `research/Research_Render_Report.md` и дублируется в раздел
«План портирования» `port_status.md`):

1. **Выбранная стратегия** и обоснование (одна строка классификации +
   почему отклонены альтернативы).
2. **Дефайн порта** — имя, выбранное по стилю дефайнов движка.
3. **Список изменений по файлам/модулям**: контекст, загрузчик, шейдерный
   компилятор, рендер-модули, бинды бэкбуфера.
4. **Таблица отключаемых по умолчанию эффектов** (из 3.2) с механизмом
   отключения каждого (3.3).
5. **Таблица конверсии шейдеров** (из 2.4): файл → версия → действие.
6. **Милистоуны** (каждый — коммит, как в AGENTS.md):
   - M1: ES3-контекст создаётся, кадр очистки цветом;
   - M2: загрузчик и шейдерный пайплайн на ESSL, базовая сцена рендерится;
   - M3: все несовместимые вызовы заменены/исключены, визуальных
     регрессий в основных сценах нет;
   - M4: эффекты по таблице отключены/включены, логирование отключений;
   - M5: прогон на устройстве (обе архитектуры по возможности);
   - далее — стыковка с основным планом: этап 1 (сборка под Аврору),
     этап 2 (FBO-модуль поверх выбранного рендера).
7. **Риски и оговорки** на каждый милистоун (раздел 8).
8. **Критерий готовности к кодированию**: план согласован с пользователем
   (в manual-режиме — обязательно явное подтверждение; в auto — зафиксирован
   в `port_status.md`).

## 8. Сквозные оговорки и риски

- **Производительность мостов.** gl4es и Zink добавляют оверхед; immediate
  mode через gl4es батчится, но тяжёлые сцены проседают. Критерий
  приемлемости (целевой FPS на основных сценах) зафиксируй в отчёте до
  выбора моста — иначе решение нечем проверить.
- **Точность шейдеров на мобильных GPU.** В ESSL фрагментные шейдеры
  по умолчанию без `highp`; артефакты на больших координатах/UV — типовая
  проблема портов. Правило: `highp` для позиций/матриц/больших UV,
  `mediump` — только осознанно.
- **gl4es — ограничения.** Покрытие API неполное (display lists частично,
  часть расширений эмулируется дорого), GLES3-бэкенд моложе и менее
  обкатан, чем GLES2. Перед выбором S2 прогнать тест сборки проекта
  с gl4es и снять список «not implemented» из лога — это часть прототипа.
- **Zink — ограничения.** Требует Vulkan-драйвер с фичами профиля Zink;
  Vulkan есть не на всех устройствах Авроры; сборка Mesa под таргеты —
  отдельный большой фронт работ; пакет раздувается на десятки МБ;
  wayland-egl-путь на устройстве проверяется прототипом до коммита
  на стратегию.
- **ANGLE — ограничения.** Не исполняет desktop GL. Тяжёлая система сборки
  (depot_tools/gn), большой чекаут, нетривиальная интеграция в RPM.
  Рассматривать только после S1 как запасной драйвер или как десктопный
  полигон.
- **FBO-модуль поверх выбранной стратегии.** Требования этапов 2–4
  AGENTS.md сохраняются при любой стратегии. При S2 точки перехвата
  (`glBindFramebuffer(0)`) работают сквозь мост — проверить на прототипе.
  При S3/S4 перепроверить «опасные места» из AGENTS.md (кеширование
  состояния GL мостом, `glUseProgram` движка перед отрисовкой).
- **Песочница и пакет.** Дополнительные .so мостов → `/usr/share/%{name}/lib`,
  patchelf/rpath, `__requires_exclude`, прогон rpm-validator — по
  разделу «Сборка пакета» AGENTS.md. Тексты лицензий бандлируемых
  библиотек включить в пакет.
- **Сжатые текстуры.** S3TC-ассеты на мобильных GPU обычно не поддерживаются:
  либо готовить ETC2/ASTC-варианты, либо CPU-распаковка (медленно,
  память). Проверить, какие форматы грузит игра.
- **Мердж с апстримом.** Чистый порт (S1) конфликтует с апстрим-обновлениями
  сильнее, чем мост (S2/S3). Если проект активно развивается и планируется
  трекать апстрим — учитывать при выборе.
- **Одна стратегия в одном бинаре.** Комбинации (gl4es + частичный чистый
  порт) допустимы, но только как осознанное решение с фиксацией в отчёте.
