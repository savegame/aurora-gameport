# Сборка под Аврору: sfdk, таргеты, зависимости

Этот документ читай на **этапе 1** (сборка под Аврору) и далее при
добавлении новых зависимостей. Здесь: правила работы с AuroraSDK
(только sfdk), выбор таргетов, рецепты build-init/prepare/build,
структура каталога сборки и правила оформления зависимостей в
spec-файле. Специфика SDL2/GLFW3 — в `docs/sdl2_aurora.md` и
`docs/glfw3_aurora.md`; подпись и валидация пакета — в разделах
«Подпись пакета» и «Валидация пакета» в AGENTS.MD.

## Тулчейн AuroraSDK

Путь до утилиты **sfdk** берётся из `port_config.json` (поле `sfdk`).
Далее sfdk используется для работы с AuroraSDK.

### Ограничение: только sfdk
Вся работа со сборочным окружением Авроры — ТОЛЬКО через утилиту sfdk
(путь из `port_config.json`). ЗАПРЕЩЕНО напрямую трогать сборочный
движок и его инфраструктуру: docker/VirtualBox-контейнеры и VM,
ssh в движок, known_hosts, конфиги движка и SDK. Любые проблемы с
движком решаем командами sfdk (`sfdk engine start/stop/status` и т.п.)
или эскалируем пользователю. Обычные инструменты командной строки
(cmake, ninja, git, компиляторы хоста) запускать можно.

### Получение списка таргетов
  `sfdk engine exec sb2-config -l`
  Вывод содержит строки вида `AuroraOS-5.1.6.65-MB2-aarch64`, где
    - `5.1.6.65` — версия ОС
    - `aarch64` — архитектура таргета
  Также будут таргеты с суффиксом `.default` — это снапшоты, их НЕ
  используем при сборке: SDK автоматически создаёт снапшот из таргета
  и использует его.
  При получении списка таргетов выбираем 2 таргета с архитектурами armv7hl
  и aarch64, исходя из условия, что их версии одинаковы и >= 5.1.0.0
  (либо соответствуют полю `target` из `port_config.json`, если пользователь
  задал конкретную версию).
  Полученные таргеты используются в связке со sfdk для вызова команд сборки:
  ```
  sfdk -c target=<target_name> <command>
  ```
  где <target_name> — имя таргета, например `AuroraOS-5.1.6.65-MB2-aarch64`,
  а <command> — команда для таргета: `build-init`, `prepare`, `build`
  (описаны ниже).

### Инициализация, подготовка и сборка
В рецептах ниже вместо <target_name> подставлять имя одного из таргетов.
По умолчанию отлаживать и тестировать сборку для архитектуры `aarch64`.
1. Перед началом сборки вызвать инициализацию:
   `sfdk -c target=<target_name> build-init`
   build-init можно вызвать один раз в репозитории, он создаёт конфигурацию
   для сборки; далее используются только шаги prepare и build.
2. Подготовка сборки `prepare`:
   `sfdk -c target=<target_name> prepare` — выполняется установка
   зависимостей `BuildRequires` из spec-файла в таргет, а также этап
   `%prep` из spec-файла.
3. Сборка RPM-пакета `build`:
   `sfdk -c target=<target_name> build` — выполняются все этапы из секции
   `%build`; после удачной сборки происходит упаковка в RPM.

## Структура каталога сборки

Во всех местах, где это предусмотрено системой сборки, собранные бинарные
артефакты, объектные файлы и сгенерированные промежуточные файлы должны
попадать в директорию `build` в корне репозитория. Внутри неё — папки
`aarch64` и `armv7hl`, в которых лежат отдельные папки для всех собранных
зависимостей. Например, если собирается библиотека `libfoo`, то собранная
под aarch64 библиотека и артефакты сборки (объектники, cmake-файлы и прочее)
лежат в `build/aarch64/libfoo/*`.

## Зависимости сборки

### cmake
Если портируемый проект собирается с cmake, добавляем BuildRequires:
```
BuildRequires: ninja
BuildRequires: cmake
BuildRequires: extra-cmake-modules
```
и при вызове команды конфигурации cmake передаём путь до ninja
(специфика платформы), например:
```
cmake \
    -G Ninja \
    -DCMAKE_MAKE_PROGRAM=/usr/bin/ninja \
    <другие флаги сборки> \
    -S mygame \
    -B build/%{_arch}/mygame
```

### SDL2 / GLFW3
Форки с фиксами под ОС Аврора — обязательны, если проект использует
эти фреймворки. BuildRequires и скрипты сборки/установки:
- SDL2 — `docs/sdl2_aurora.md` (подмодуль `libsdl`);
- GLFW3 — `docs/glfw3_aurora.md` (подмодуль `glfw3`).

### Прочие зависимости
Проекту могут потребоваться другие зависимости, кроме описанных здесь.
Действуем следующим образом:
- Если это SDL2 — берём модифицированную (см. `docs/sdl2_aurora.md`).
- Если это библиотека (например ogg, vorbis, curl и т.п.) — найти
  репозиторий с ней, выгрузить как подмодуль нужной версии, добавить
  скрипты сборки в секцию `%build`, а установку делать в секции `%install`
  при помощи команды `install` в папку `/usr/share/%{name}/lib/`.
- Если это система сборки (waf) — сначала выгрузить и собрать эту утилиту,
  положить как подмодуль в папку `tools`.
- Если зависимость доступна в репозитории ОС Аврора — пробуем использовать
  её, если версия подходит (желательно подкрутить скрипты сборки, чтобы
  версия из репозитория подходила). Проверка доступности зависимости:
  выполняем команды zypper внутри снапшота нужного таргета (т.е. с суффиксом
  `.default`), например:
  ```
  sfdk engine exec sb2 -t AuroraOS-5.1.3.85-MB2-aarch64.default -R -m sdk-install zypper se scons
  ```
  Если нашли — добавляем в `BuildRequires`, причём желательно использовать
  имя pkgconfig-файла вместо названия пакета: так spec становится гибче
  и не зависит от версии таргета:
  ```
  BuildRequires: pkgconfig(openal)
  ```
  Если зависимость не предоставляет pkgconfig-файлов — пишем по названию
  пакета:
  ```
  BuildRequires: scons
  ```

### Исключение добавленных зависимостей из валидации разрешённых библиотек

Валидатор пакета (rpm-validator) проверяет, с какими библиотеками
линкуется приложение: часть системных библиотек разрешена как
зависимость, часть — нет. Правило `__requires_exclude` в spec-файле
убирает библиотеку из автоматически вычисляемых Requires пакета.
Воркфлоу:

1. Находим зависимости проекта и либо добавляем их в `BuildRequires`
   (если они есть в репозитории ОС Аврора), либо собираем сами
   (подмодуль, установка в `/usr/share/%{name}/lib`).
2. **Зависимость собрана нами** (не из репозитория Авроры) — сразу
   прописываем её в `__requires_exclude`: она лежит внутри нашего
   пакета, и система не должна искать её как внешнюю зависимость.
3. **Зависимость из репозитория Авроры** — сначала собираем пакет,
   подписываем и прогоняем валидатор (см. «Подпись пакета» и
   «Валидация пакета» в AGENTS.MD). Многие системные библиотеки
   разрешены как зависимости напрямую — например `dbus-1`, `GLESv2`,
   многие Qt-библиотеки: их линкуем из системы и в
   `__requires_exclude` НЕ добавляем.
4. Только если валидатор сообщил, что библиотека не разрешена как
   зависимость линковки — прописываем её в `__requires_exclude`
   и копируем саму библиотеку из таргета внутрь нашего пакета,
   в `/usr/share/%{name}/lib` (см. «Валидация пакета» в AGENTS.MD).

Формат правила: все библиотеки записываются одним регулярным
выражением (например, для libfoo.so.1 и libbar.so.1):
```
%define __requires_exclude ^libfoo.*\\.so.*|libbar\\.so.*$
```
