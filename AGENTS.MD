# AGENTS.md — спецификация порта игры на ОС Аврора

> Этот файл — эталонный шаблон. Не редактируй его в ходе работы.
> Все данные конкретной сессии (проект, SDK, таргет, статус работ)
> хранятся в рабочих файлах `port_config.json` и `port_status.md`
> в корне репозитория (см. разделы ниже).
> В `docs/` лежит `GLES3_Render_Research_Plan.md` — тоже
> эталонный документ, не редактируй его: это методика условного этапа
> «Мобильный рендер», применяется, если проект несовместим с GLES3.

## Старт сессии

1. Ищи в корне репозитория файл `port_config.json`. Если он есть —
   прочитай и используй значения оттуда.
2. Если файла нет — СПРОСИ у пользователя:
   - URL репозитория проекта;
   - путь до AuroraSDK (утилита sfdk лежит по адресу
     `<путь_до_SDK>/bin/sfdk`; допустимо указать и полный путь
     до бинаря sfdk);
   - желаемую версию таргета, если есть пожелания (по умолчанию
     берём таргеты крайней доступной версии >= 5.1.0.0);
   - режим работы: `auto` (автоматический) или `manual` (ручной);
   - идентификаторы приложения: `app_orgname` (обратное доменное имя
     организации/разработчика, например `org.example`), `app_appname`
     (имя приложения/пакета), `app_launcher_name` (отображаемое имя
     в лаунчере).
   Запиши ответы в `port_config.json` в корне репозитория:
   ```json
   {
     "project_url": "https://github.com/example/mygame",
     "sfdk": "/path/to/AuroraSDK/bin/sfdk",
     "target": "AuroraOS-5.1.3.85-MB2",
     "mode": "auto",
     "app_orgname": "org.example",
     "app_appname": "mygame",
     "app_launcher_name": "My Game"
   }
   ```
   Поле `target` указывается без суффикса архитектуры — архитектура
   (`aarch64` / `armv7hl`) подставляется при вызове sfdk.
   Поле `mode` определяет режим работы (см. «Поэтапный план»);
   допустимые значения: `"auto"`, `"manual"`.

   СТРОГОЕ ПРАВИЛО: НЕ начинать работу (разведку, правки кода,
   сборку), пока не выяснены ВСЕ данные для `port_config.json`,
   включая идентификаторы приложения (`app_orgname`, `app_appname`,
   `app_launcher_name`). Эти значения определяют имя пакета
   (`%{_app_orgname}.%{_app_appname}` в spec-файле), desktop-файл,
   а главное — разрешённые пути записи песочницы
   (`~/.local/share/<app_orgname>/<app_appname>` и т.д.): правки путей
   в коде и упаковка обязаны использовать ровно эти значения.
   Значения из `port_config.json` должны совпадать с define'ами
   spec-файла (`_app_orgname`, `_app_appname`, `_app_launcher_name`)
   и с дефайнами, передаваемыми в код (`AURORA_ORG`, `AURORA_APP`).
3. Ищи файл `port_status.md`. Если он есть — прочитай его первым
   делом: там зафиксированы результаты анализа, план портирования,
   чеклист выполненного и известные ошибки. Продолжай работу с того
   места, где остановился чеклист. Формат файла описан в разделе
   «Файл статуса port_status.md».

## Роль

Ты — кодинг-агент. Работаешь с исходным кодом проекта, указанного
в `port_config.json` (поле `project_url`).
Твоя задача — исследовать структуру рендеринга проекта и портировать
его на ОС Аврора (Wayland-композитор).

## Цель портирования
Проект: берётся из `port_config.json`.
Пример: https://github.com/example/mygame
Тег: посмотри, какие есть ветки и теги, бери последний стабильный
релиз.

## Платформа и окружение
- Язык: C++17
- Графический API: GLES3
- Оконная система: Wayland-композитор БЕЗ поддержки xdg-shell.
  Доступные протоколы: wl-shell, qt-extended-surface.
- Исходный код проекта: корень репозитория.

Параметры дисплея (нативная развёртка, transform) клиент получает
от композитора при запуске на устройстве — не задавай их заранее
и не хардкодь.

### EGL: дефайн WL_EGL_PLATFORM
В таргетах Авроры заголовок `EGL/eglplatform.h` по умолчанию выбирает
X11-платформу (ветка `__unix__`) и тянет `#include <X11/Xlib.h>`,
которого в таргете нет — компиляция любого файла, включающего
`EGL/egl.h`/`EGL/eglplatform.h`, падает. Поэтому при сборке под Аврору
(Wayland) обязательно объявляй дефайн `WL_EGL_PLATFORM` (например,
`add_compile_definitions(WL_EGL_PLATFORM)` в CMake): тогда нативные
типы EGL становятся `wl_display` / `wl_egl_window`, что соответствует
нативным хендлам Wayland (см. `SDL_SysWMinfo` → `info.wl.display`,
`info.wl.egl_window`). Добавляй дефайн только в платформенную ветку
порта (бандл-сборку под Wayland) — десктопные сборки с X11 он ломать
не должен.

### Звук (PulseAudio)
Перед инициализацией звука в проекте обязательно выставить
env-переменную `PULSE_PROP_media.role=x-maemo` — без неё звук
на платформе работает некорректно. Если в проекте есть SDL2:
```c
SDL_setenv( "PULSE_PROP_media.role", "x-maemo", 1 );
```
Если SDL2 нет — обычный `setenv("PULSE_PROP_media.role", "x-maemo", 1)`.
Выставлять строго ДО инициализации звуковой подсистемы движка.

### Пути записи (песочница)
Приложение работает в песочнице и может писать только в каталоги:
- `~/.local/share/org.example/appname`
- `~/.cache/org.example/appname`
- `~/.config/org.example/appname`

где `org.example` — обратное доменное имя организации или
разработчика, `appname` — имя приложения (см. «Имя пакета
и песочница»). Все пути, куда проект пишет что-либо (конфиги, кэши,
сохранения, логи, аддоны, скриншоты, реплеи), обязаны разрешаться
в эти каталоги. Пути, найденные в исходниках и не попадающие
в разрешённые, исправляются (под дефайном порта) ещё на этапе
сборки — до первого запуска на устройстве.

## Техническое решение: поворот через промежуточный FBO

Поворот реализуется на стороне клиента через промежуточный FBO:
сцена рендерится в текстуру, перед swap текстура выводится на экран
квадом с трансформацией. Композитор буфер не модифицирует — поворот
контента является обязанностью клиента.

## Правила внесения изменений

- Изменения только в слое рендера и платформенной интеграции.
  Логику игры не менять.
- GLES3, без MSAA.
- Весь код порта закрывай дефайном: имя подбери по стилю дефайнов
  в исходниках движка (например, AURORA_FBO). По ветке #else
  остаётся нетронутый старый код без FBO. Сборка без дефайна =
  движок работает ровно как раньше. Код порта НЕ должен ломать
  основную ветку движка.

## Поэтапный план

Режим работы берётся из `port_config.json` (поле `mode`): `"auto"` —
автоматический, `"manual"` — ручной. Если поле не задано — СПРОСИ
пользователя и запиши ответ в конфиг.
В ручном режиме без подтверждения ПОЛЬЗОВАТЕЛЯ к следующему этапу
не переходить. В автоматическом режиме, если не требуется запуск
на устройстве и верификация глазами, — переходим к следующему этапу.
Перед началом нулевого этапа изложи пользователю план действий
и предупреди, на каком этапе понадобятся действия от пользователя.
Перед этапом 0 также согласуй с пользователем использование модуля
запрета гашения экрана (этап «Гашение экрана (MCE)» — условный, но
рекомендуемый): брать как есть из `examples/mce/` или адаптировать
под конкретный движок/API.
Ход работы и результаты каждого этапа фиксируй в `port_status.md`.
После каждого завершённого этапа делай git-коммит с осмысленным
описанием сделанного. Если этап разбит на подпункты и подпункт был
значительным — коммить и после него, чтобы история позволяла
откатиться к любому стабильному состоянию.

### Этап 0. Начальное исследование проекта
- Выяснить, каким инструментом собирается проект.
- Совместим ли проект с GLES3 или мобильным Vulkan. Если проект
  не совместим (например, поддерживает только desktop OpenGL) —
  остановиться и спросить пользователя, нужно ли запускать
  отдельный этап «Мобильный рендер» (см. ниже).
- Какие есть зависимости и где их взять (сначала проверить
  репозиторий ОС Аврора; если нет — найти репозиторий с нужной
  зависимостью).
- Найти в исходниках все места, где проект пишет файлы (конфиги,
  кэши, сохранения, логи, аддоны, скриншоты, реплеи), и зафиксировать
  фактические пути — на предмет соответствия разрешённым путям
  песочницы (см. «Платформа и окружение» → «Пути записи (песочница)»).
- Детальный чеклист разведки — в разделе «Разведка
  рендер-пайплайна движка».

### Этап «Мобильный рендер» (условный)
Выполняется только по решению пользователя после этапа 0.
Сгенерировать документ `Research_Render_Report.md`, в котором
описать, какой графический API используется в проекте, и возможно
ли его переписать на GLES3/Vulkan. GLES3 в приоритете (совместим
со всеми устройствами, Vulkan — с большинством).
Методика исследования — в документе `docs/GLES3_Render_Research_Plan.md`:
инвентаризация GL-профиля, аудит эффектов (несовместимые с GLES3 эффекты
по умолчанию отключаются штатными средствами движка), матрица выбора
стратегии (чистый GLES3-порт в приоритете; gl4es для GL 1.x/2.x;
Zink — desktop GL поверх Vulkan — запасной путь для тяжёлых GL 3.x/4.x;
ANGLE — GLES поверх Vulkan, запасной драйвер и десктопный полигон),
прототипирование и формализация плана реализации.

### Этап 1. Сборка под Аврору
- Собрать зависимости проекта тулчейном под aarch64 и armv7hl.
- Собрать проект тулчейном под aarch64 и armv7hl.
- Зависимости SDL2/GLFW3 — только из репозиториев с фиксами под
  Аврору (см. раздел «Сборка пакета»).
- Перед инициализацией звука выставлена `PULSE_PROP_media.role=x-maemo`
  (см. «Платформа и окружение» → «Звук»).
- Пути записи (конфиги, кэши, сохранения, логи и прочее), найденные
  на этапе 0, приведены к разрешённым путям песочницы
  (см. «Платформа и окружение» → «Пути записи (песочница)»).
- Критерий: бинарь запускается на устройстве, лог чистый,
  проект рендерит в GLES3/Vulkan, звук работает.

### Этап «Гашение экрана (MCE)» (условный, рекомендуемый)
Рекомендуется для большинства портов: если в игру играют геймпадом
или подолгу не касаются экрана (катсцены, диалоги), система гасит
дисплей прямо во время игры — тач-ввода нет, бездействие засчитано.
Модуль запрета гашения через MCE решает это: пока приложение на
переднем плане, запрет периодически продлевается; при сворачивании
и штатном закрытии — отменяется. Использование модуля (как есть или
с адаптацией под движок/API) согласуется с пользователем ДО этапа 0
(см. преамбулу «Поэтапный план»).
- Взять модуль из `examples/mce/` (протокол и детали — в
  `docs/mce_display_blanking.md`), при необходимости адаптировать
  под движок.
- Включать запрет гашения, когда приложение на переднем плане.
- Отключать запрет при сворачивании (SDL_APP_WILLENTERBACKGROUND
  в SDL2, иконификация окна в GLFW) и при штатном закрытии.
- Критерий: экран не гаснет во время игры без касаний (в т.ч. при
  игре геймпадом); после сворачивания/закрытия приложения гашение
  экрана работает как обычно.

### Этап «Лаунчер (imgui)» (условный)
Выполняется, если у игры НЕТ свободно распространяемых ресурсов
(проприетарная игра): ресурсы нельзя класть в пакет, пользователь
должен указать путь к легально установленной игре — для этого нужен
лаунчер. Реализуется внутри процесса на Dear ImGui, в том же окне,
в котором потом развернётся игра (композитор убивает приложение при
исчезновении окна). Все требования — в документе
`docs/imgui_launcher.md` (структура вкладок, тач-вёрстка, браузер
ресурсов, передача окна движку, кадр «Загрузка»), тема оформления —
в `docs/imgui-theme-spec.md`.
- Окно лаунчера создаётся с теми же GL-атрибутами, что ожидает
  движок (профиль ES3, RGBA8, depth 24, stencil 8, doublebuffer),
  и НЕ пересоздаётся при старте игры: после кадра «Загрузка» ImGui
  выгружается, а окно и GL-контекст передаются движку.
- Базовая вкладка: выбор папки ресурсов с валидацией, после выбора —
  кнопки запуска (игра + отдельные кнопки модов/DLC, если есть).
- Вкладка настроек: как минимум слайдер коэффициента FBO (0.25–2.0).
- Вкладка «О программе»: дисклеймер AS IS и ссылка на телеграм-канал
  (см. `docs/imgui_launcher.md`).
- Кнопки и шрифт — под тач: размеры от физического DPI устройства.
- Критерий: на устройстве лаунчер позволяет выбрать ресурсы и
  запустить игру; после «Старта» показывается кадр «Загрузка», затем
  игра стартует в том же окне; выбранный путь и настройки
  сохраняются между запусками.

### Этап 2. Интеграция FBO-модуля
- Реализовать FBO-модуль по разделу «Требования к FBO-модулю».
- Перевести рендер сцены на FBO: заменить бинды бэкбуфера
  (`glBindFramebuffer(GL_FRAMEBUFFER, 0)` и аналоги, найденные
  при разведке) биндом нашего FBO.
- Реализовать отрисовку квада с текстурой FBO на экран перед swap.
- Подменить источник размера экрана размерами FBO (только в логике
  движка; EGL не трогаем).
- На этом этапе FBO ещё НЕ обрабатывает смену поворота контента
  и изменение размеров рендеринга (даунскейл/апскейл) — это этап 3.
- Критерий: FBO работает в целом — игра рендерится в FBO и выводится
  квадом на экран без визуальных регрессий (проверка на устройстве —
  в ручном режиме).

### Этап 3. Поворот и ресайз контента
- Подписаться на wl_output::geometry или на события ориентации
  SDL2 (см. раздел «Требования к FBO-модулю») и пересчитывать
  трансформацию с учётом типа дисплея.
- Выставлять wl_surface.set_buffer_transform (сниппет для SDL2 —
  ниже).
- Приводить физическую ориентацию устройства к «родной» для игры
  по маппингу (см. «Маппинг ориентаций под ориентацию игры»).
- Привязать к FBO изменение размеров рендеринга (даунскейл/апскейл,
  ресайз окна, перенос на другой дисплей): при изменении размеров FBO
  движок должен получить именно размер FBO вместо размеров реального
  окна и корректно его обработать — вызвать обработчики resize для
  перерисовки UI (см. «Размер окна и буфера при повороте»).
- Критерий: контент корректно поворачивается во всех ориентациях,
  при смене размеров FBO игра получает размер FBO (а не реального
  окна) и верно его обрабатывает, UI перерисовывается под новые
  пропорции, системные жесты работают.

#### set_buffer_transform из SDL2-приложения
Чтобы выставить трансформацию буфера из приложения на SDL2:
1. Бинарь должен линковаться с wayland-client — в spec-файле нужен
   `BuildRequires: pkgconfig(wayland-client)` (входит в список
   зависимостей SDL2, см. раздел «Сборка пакета»).
2. В файле, где дёргается API set_buffer_transform, добавить:
   `#include <wayland-client.h>`
3. Передавать трансформацию буфера (псевдокод как пример; в конкретном
   случае `orientation` может быть enum движка или реальным углом
   поворота в градусах):
```c
struct wl_surface *surface = NULL;
SDL_SysWMinfo wmInfo;

if( !sdlWindow ) // SDL_Window pointer
	return;

SDL_VERSION( &wmInfo.version );
if( !SDL_GetWindowWMInfo( sdlWindow, &wmInfo ))
	return;
if( wmInfo.subsystem != SDL_SYSWM_WAYLAND )
	return;

surface = wmInfo.info.wl.surface;
if( !surface )
	return;

switch( orientation )
{
case landscape:
	wl_surface_set_buffer_transform( surface, WL_OUTPUT_TRANSFORM_90 );
	break;
case inverted_portrait:
	wl_surface_set_buffer_transform( surface, WL_OUTPUT_TRANSFORM_180 );
	break;
case inverted_landscape:
	wl_surface_set_buffer_transform( surface, WL_OUTPUT_TRANSFORM_270 );
	break;
default: // portrait
	wl_surface_set_buffer_transform( surface, WL_OUTPUT_TRANSFORM_NORMAL );
	break;
}
```

### Этап 4. Трансформация ввода
- События ввода (мышь, тач) приходят от композитора (через события
  SDL2/GLFW) в нативных координатах дисплея — поворот контента
  на них не влияет.
- Перед передачей события движку применять к его координатам
  трансформацию, обратную текущему повороту FBO.
- В той же трансформации учитывать коэффициент масштабирования,
  с которым FBO выводится на экран (даунскейл/апскейл).
- Движок должен получать события ввода в локальных координатах FBO —
  только после преобразования отдавать их на внутреннюю обработку
  движка.
- Точку перехвата ввода найти заранее — при разведке (см. раздел
  «Разведка рендер-пайплайна движка», п.8).
- Ввод от геймпада (если он есть в коде проекта) НЕ трансформируем:
  ему всё равно, какая ориентация экрана, — события геймпада идут
  в движок как есть.
- Критерий: тач попадает в отображаемый элемент при любой
  ориентации и любом масштабе рендеринга.

### Этап «Тач-UI (виртуальный геймпад)» (условный)
Выполняется по решению пользователя после этапов 3–4 (поворот
буфера и трансформация тача уже работают) — если в игре нет своего
тач-UI. Требования и рекомендации — в `docs/touch_ui.md`.
- Сначала — отдельная разведка с отчётом в `port_status.md`
  (раздел «Результаты анализа»): как движок вызывает action'ы,
  как обрабатывает мышь, куда встраивать отрисовку оверлея, есть
  ли зачатки тач-UI в апстриме. Без зафиксированной разведки
  интеграцию не начинать — она должна быть простой и без ошибок.
- Левая половина экрана — плавающий виртуальный стик (центр
  появляется в точке касания), правая — тачпад камеры (эмуляция
  мыши); кнопка выхода в меню обязательна.
- Кнопки действий вызывают реальные action движка, а не эмулируют
  клавиши/кнопки геймпада — иначе сломаются при перебинде.
- Мультитач обязателен: отслеживание по fingerId; если кнопки
  рисуются ImGui, нажатия обрабатывать самостоятельно по rect'ам
  UI-элементов.
- Оверлей — отдельным модулем, рисуется последним; лучше — своим
  UI-FBO с размерами экрана (чёткий при любом скейле рендера).
- Размеры элементов — в мм от физического DPI устройства.
- Критерий: в игру можно играть без геймпада и клавиатуры — стик,
  камера и кнопки действий работают одновременно несколькими
  пальцами, кнопка меню доступна всегда.

### Этап «Встроенная клавиатура» (условный)
Выполняется по решению пользователя — если в игре есть текстовый

## Разведка рендер-пайплайна движка

До любых изменений кода исследуй движок и зафиксируй ответы
в `port_status.md`. Ничего не меняй, пока разведка не завершена.

1. Какой графический API использует движок. Совместим ли он с GLES3.
   Если проект рендерит только через чистый OpenGL — стоп, эскалация
   пользователю. По решению пользователя открывается этап
   «Мобильный рендер» — исследование по `docs/GLES3_Render_Research_Plan.md`
   (см. «Поэтапный план»).
2. Как устроен рендер-пайплайн до вызова swap. Найди вызов swap:
   glSwapBuffers, SDL_GL_SwapWindow, irrlicht endScene или аналог —
   определи, какой именно используется в этом движке.
3. Куда рисуется игровая сцена: напрямую в бэкбуфер (direct draw)
   или движок уже рендерит в своё FBO и затем swap. Движковое FBO
   НЕ переиспользуем и НЕ модифицируем: мы подменяем только прямой
   вывод на экран (бинд бэкбуфера), более ничего. Для движка наш FBO
   выглядит как экран: он по-прежнему отрисовывает своё 3D-FBO,
   а затем свой UI — уже в наш FBO, как если бы рисовал напрямую
   на экран.
4. Как движок выставляет буфер рендеринга. На чистом GLES ищи
   glBindFramebuffer(GL_FRAMEBUFFER, 0) — бинд 0 означает рендер
   в бэкбуфер (на экран). Все такие места — кандидаты на замену
   бинда 0 биндом нашего FBO.
5. Как движок узнаёт размер окна/экрана: глобальная переменная,
   запрос через SDL2 API, другой путь. Важно: размер ОКНА и размер
   ЭКРАНА (дисплея) — разные вызовы API, движок может дёргать оба
   (например, SDL_GetWindowSize и SDL_GetDisplayBounds/
   SDL_GetCurrentDisplayMode) — найди все такие места, иначе часть
   подмен будет пропущена. Сюда позже внедряется подмена размера
   закешированным размером нашего FBO.
6. Сколько путей вывода графики у движка. Обычно swap один за кадр,
   но возможны раздельные режимы (меню / игра) с разными путями
   вывода — найди все.
7. Использует ли движок собственный API для render target. Приоритет
   выбора средств: сначала существующий API движка — так меньше шанса
   навредить, — но только если его вызов не переусложняет кросс-
   зависимости между модулями. Иначе — чистый GLES3, если это легко
   и уместно.
8. Где движок забирает события ввода (мышь/тач): SDL_PollEvent,
   GLFW-колбэки, свой слой абстракции. Это кандидат на точку
   перехвата для трансформации координат (см. «Этап 4.
   Трансформация ввода»).
9. Где и как движок кэширует GL-состояние (call bridge, dirty-флаги,
   свои обёртки над gl-вызовами). Зафиксируй, что FBO-модуль обязан
   восстановить после вывода квада и как (через API движка или
   возвратом значений из кэша — см. «Опасные места»). Пропуск этого
   пункта дорого обходится в отладке: рассинхрон кэша (например,
   viewport) даёт дефект рендера, который по симптомам похож на
   ошибку в размерах или маппинге transform.

### Опасные места
- Состояние GL: при отрисовке нашего буфера мы выставляем свои
  glProgram. Убедись, что рендер движка не сломается: движок ожидает
  свои шейдеры. На практике большинство движков дёргают glUseProgram
  перед отрисовкой геометрии — тогда конфликта нет. Проверить
  обязательно.
- Кэшированное GL-состояние движка. Движок может кэшировать GL-state
  и пропускать «лишние» gl-вызовы (например, в irrlicht —
  COGLES2CallBridge кэширует viewport и др.). Если FBO-модуль меняет
  состояние сырыми gl-вызовами мимо этого кэша, кэш расходится с
  реальным состоянием: на следующих кадрах движок считает его уже
  выставленным и не перевыставляет — дефект живёт, пока значение не
  сменится через API движка. Правила:
  - При создании FBO-модуля сначала ищи движковые API для тех
    GL-операций, которые нужны модулю (viewport, биндинги
    framebuffer/текстур, флаги состояния), и используй их вместо
    сырых вызовов GLES3 — тогда кэш движка остаётся согласованным
    сам (пример: в порту RE3 для этого использовался API librw
    вместо сырого GLES3). Это заметно снижает риск рассинхрона.
  - Если движкового API нет и без сырых вызовов не обойтись — всё,
    что модуль трогает при выводе квада (glViewport, биндинги
    framebuffer/текстур/VAO, флаги depth/stencil/blend/scissor/cull),
    восстанавливай после блита, возвращая значения из кэша движка.
  - Не вычитывай состояние через glGet* каждый кадр — это дорого
    и не нужно: смотри, как состояние кэшируется в движке, и бери
    значения оттуда.
  Прецедент (порт STK): движок кэшировал glViewport, а FBO-модуль
  при выводе квада выставлял viewport сырым gl-вызовом мимо кэша
  и не восстанавливал его. На следующем кадре движок считал свой
  viewport уже активным и рисовал не в тот viewport: на экране —
  часть кадра, растянутая и смещённая, при этом все читаемые через
  API размеры были правильными — отладка сначала шла по ложному
  следу (размеры, маппинг transform).
- Маппинг «ориентация → buffer transform», зашитый под один тип
  панели: на портретной панели landscape = 90°, на ландшафтной = 0°
  (см. таблицу в «Маппинг ориентаций под ориентацию игры»). Если
  захардкодить 90/270, рендер ломается на ландшафтных панелях и при
  переносе окна на внешний монитор. Тип панели определяй по нативному
  разрешению текущего дисплея, но пересчитывай его ОДИН раз при
  инициализации и далее только при смене дисплея (перенос окна на
  другой output) — по событию смены дисплея фреймворка, если оно есть
  (у SDL2 и GLFW3 такие события/API есть). Не пересчитывай тип панели
  на каждый поворот и тем более на каждый кадр: нативные размеры
  дисплея фреймворк сам кэширует при получении mode от композитора,
  частые запросы ничего не дают.
- Асимметрия канонизации путей при симлинковом дереве ресурсов:
  при установке пакета на Авроре создаются симлинки на все файлы
  пакета, и приложение в рантайме работает уже с симлинками — со
  всеми ресурсами, библиотеками и контентом, установленными в
  `/usr/share/org.example.appname/*` (реальные файлы лежат отдельно,
  например в `/opt/app/<name>`). Если одна часть движка канонизирует
  путь (realpath), а другая сравнивает с ним текстовый путь,
  строковое сравнение промахивается: ресурс (материал, текстура,
  модель) не находится и молча подставляется дефолтный — без ошибок
  в логе. Правило: либо канонизируй пути во всех лоадерах
  симметрично, либо нигде; любые строковые сравнения путей — только
  после одинаковой канонизации обеих сторон.

## Требования к FBO-модулю

API модуля:
- создание/уничтожение (формат буфера под требования движка: цвет +
  буфер глубины + стенсил-буфер, если он используется в движке, —
  до трёх буферов; если есть возможность совместить глубину и стенсил
  в одном буфере, не сломав рендер (GL_DEPTH24_STENCIL8 и аналоги), —
  используем совмещённый);
- resize;
- биндинг/анбиндинг FBO как активной цели рендеринга;
- доступ к текстуре результата;
- возврат своих размеров (подмена размера работает только в логике
  движка; EGL не трогаем, остаётся как есть);
- коэффициент масштабирования, по умолчанию 1.0;
- задать / получить угол поворота (значение enum wl_output_transform;
  точные градусы не нужны);
- метод отрисовки квада с текстурой FBO на экран.

Вывод на экран:
- по возможности использовать API отрисовки движка; если проще
  GLES3 — использовать GLES3;
- только квадом с текстурой FBO. glBlitFramebuffer НЕ использовать:
  у блита нет ни поворота, ни масштабирования — вся трансформация
  делается при отрисовке квада;
- без MSAA (тяжёлый для мобильного GPU, плохо совместим с FBO);
- матрица поворота применяется ТОЛЬКО в вершинном шейдере и ТОЛЬКО
  к позициям вершин: квад полноэкранный в NDC, углы (-1,-1)..(1,1) —
  левый нижний и правый верхний углы экрана в текущей ориентации,
  никакой проекционной матрицы нет (единичная). UV проходят в
  пиксельный шейдер как записаны в вершинах, БЕЗ каких-либо
  модификаций — никаких матриц и пересчётов UV во фрагментном
  шейдере. Так как поворачивается геометрия, видимый поворот контента
  равен углу матрицы напрямую и совпадает со значением, передаваемым
  в wl_surface.set_buffer_transform (одно и то же значение enum
  wl_output_transform идёт и в set_rotation, и в buffer transform);
- кешировать всё, что можно: буферы вершин и индексов квада
  создаются один раз и переиспользуются; матрицы поворота для всех
  ориентаций готовятся заранее; поворот контента выполняется
  готовой матрицей, передаваемой в вершинный шейдер; шейдеры
  компилируются один раз и переиспользуются. Выбор матрицы
  происходит НЕ в отрисовке кадра, а в методе set_rotation самого
  FBO-модуля: он один раз переключает активную матрицу/состояние,
  и отрисовка использует уже готовое. Главное правило: никаких
  динамических пересчётов каждый кадр и никаких выделений памяти
  в кадре (под вершины, индексы и прочее) — в отрисовке нет ни
  одного условия и проверки, все данные готовы до начала кадра.
  Допустимое исключение: если движок сам опрашивает ориентацию
  дисплея каждый кадр, тогда set_rotation придётся вызывать перед
  каждым кадром — тут ничего не поделать.

### Поворот устройства: output transform
- Композитор сообщает о повороте через событие wl_output::geometry,
  поле transform (enum wl_output_transform). Событие приходит при
  бинде wl_output и при каждом изменении свойств.
- Значения enum wl_output_transform:
    0 NORMAL        — нет трансформации
    1 _90           — 90° против часовой стрелки
    2 _180          — 180° против часовой стрелки
    3 _270          — 270° против часовой стрелки
- Это только информация. Композитор буфер не поворачивает. Реакция —
  на стороне клиента.
- Если движок работает через фреймворк (SDL2, GLFW), события поворота
  приходят через его собственный API и с его собственными значениями
  enum — например, в SDL2 это событие SDL_DISPLAYEVENT_ORIENTATION
  со значениями SDL_DisplayOrientation вместо wl_output_transform.
  Тогда сырые wl_output-события не обрабатываем. Подробности —
  в подразделе «Если события ориентации приходят от SDL2 / GLFW».

### Реакция клиента: buffer transform
- Клиент отрисовывает контент уже повёрнутым и сообщает композитору:
  wl_surface.set_buffer_transform(transform), значение из того же
  enum wl_output_transform.
- Значение вне enum → protocol error invalid_transform.
- По buffer transform композитор узнаёт ориентацию контента и может
  скорректировать системные жесты (сворачивание, вызов верхнего меню).

### Типы дисплеев и интерпретация transform
- Дисплеи бывают портретные (W < H) и ландшафтные (W > H). Тип
  определяется по нативной развёртке дисплея (размеры mode события
  wl_output::mode с флагом CURRENT).
- Одно и то же значение transform имеет противоположный смысл:
  на портретном дисплее WL_OUTPUT_TRANSFORM_90 = устройство в
  ландшафтном положении; на ландшафтном дисплее = устройство в
  портретном положении.
- Окно могут переместить на другой output (подключение внешнего
  экрана). Клиент получает wl_output::geometry нового output и обязан
  заново интерпретировать transform уже по типу нового дисплея.

### Размер окна и буфера при повороте
- При повороте устройства клиенту приходит ТОЛЬКО событие смены
  ориентации (SDL_DISPLAYEVENT_ORIENTATION или wl_output::geometry
  с новым transform). Размер окна при этом НЕ меняется, событий
  resize не приходит.
- Размер окна меняется только при переносе окна на другой дисплей
  (и то не обязательно).
- Размеры буфера (ширина и высота нашего FBO) при повороте ТОЖЕ
  не меняются — они меняются только на реальный ресайз окна. Смена
  ориентации обрабатывается только трансформацией квада (готовая
  матрица поворота) и wl_surface.set_buffer_transform — одно и то
  же значение wl_output_transform идёт в оба места (см. сниппет
  этапа 3 и «Маппинг ориентаций под ориентацию игры»; для портретной
  панели ландшафтной игры это 90/270), размер буфера остаётся
  прежним.
- Если движок завязан на событие изменения размера окна (перерисовка
  UI, пересчёт layout), этот код обязан дёргаться при реальной смене
  размеров буфера (ресайз окна, перенос на другой дисплей) — события
  от платформы в этот момент может не быть. При интеграции найди
  обработчики resize в движке и вызывай их при изменении размеров FBO.

### Маппинг ориентаций под ориентацию игры
Для комфортного использования порта игра должна приводить физическую
ориентацию устройства к ближайшей «родной» для неё.
Если игра рассчитана на ландшафтную ориентацию, при получении
портретных событий выставляй соответствие:
- portrait → inverted_landscape
- inverted_portrait → landscape
Правило работает и в обратную сторону: если игра рассчитана на
портретную ориентацию, при получении ландшафтных событий:
- landscape → inverted_portrait
- inverted_landscape → portrait

При этом на портретной панели buffer transform ландшафтной игры
принимает ТОЛЬКО значения 90/270 (0/180 не используются, портретных
поворотов буфера нет): landscape/inverted_portrait → 90,
inverted_landscape/portrait → 270. Одно и то же значение
wl_output_transform идёт и в поворот квада (set_rotation), и в
wl_surface.set_buffer_transform.

Тип панели клиент определяет сам: SDL2 уже учла тип дисплея в
SDL_DisplayOrientation (см. ниже), повторно интерпретировать
wl_output::transform не нужно. Остаётся узнать нативное разрешение
текущего дисплея в пикселях — SDL_GetCurrentDisplayMode() по индексу
дисплея окна (SDL_GetWindowDisplayIndex()): H > W — портретная
панель (телефон), W > H — ландшафтная (планшет, монитор, ТВ).
Тип панели определяется один раз при инициализации (запросом
текущего дисплея) и пересчитывается ТОЛЬКО при смене дисплея —
по соответствующему событию фреймворка (у SDL2 и GLFW3 такие
события/API есть). Не пересчитывай тип панели на каждый поворот
и тем более на каждый кадр: нативные размеры дисплея фреймворк
и так кэширует при получении mode от композитора, частые запросы
ничего не дают.

Определив тип панели, сразу вычисли и закэшируй значения buffer
transform для этого типа во внутренних параметрах FBO-модуля —
например, buffer_transform_landscape = WL_OUTPUT_TRANSFORM_90 для
портретной панели или WL_OUTPUT_TRANSFORM_NORMAL для ландшафтной,
и так для каждой ориентации. Главное правило FBO-модуля одно: всё,
что можно вычислить до старта кадра, вычисляется и кэшируется
заранее — в отрисовке кадра нет никаких вычислений. Пересчёты
выполняются только по событиям: смена дисплея, смена ориентации.
А часть данных (матрицы поворота для всех ориентаций) готовится
вообще один раз на старте — при смене ориентации готовая матрица
просто выставляется как текущая.

Из двух наблюдаемых величин (системная ориентация от SDL2 и тип
панели) выводится buffer transform ландшафтной игры:

| Системная ориентация | Портретная панель | Ландшафтная панель |
|---|---|---|
| landscape | 90° | 0° |
| inverted_landscape | 270° | 180° |
| portrait | 270° | 180° |
| inverted_portrait | 90° | 0° |

(портретные системные ориентации отображены в разрешённые ландшафтные
трансформы по маппингу выше; на ландшафтной панели 0/180 — это
отсутствие поворота / переворот, портретных поворотов буфера нет).

### Если события ориентации приходят от SDL2 / GLFW
- SDL2 интерпретирует поворот сама. Событие: SDL_DISPLAYEVENT с
  подтипом SDL_DISPLAYEVENT_ORIENTATION; event.display.data1 содержит
  SDL_DisplayOrientation:
    SDL_ORIENTATION_UNKNOWN, SDL_ORIENTATION_LANDSCAPE,
    SDL_ORIENTATION_LANDSCAPE_FLIPPED, SDL_ORIENTATION_PORTRAIT,
    SDL_ORIENTATION_PORTRAIT_FLIPPED.
  Текущее значение также доступно через
  SDL_GetDisplayOrientation(displayIndex).
  Т.е. SDL2 уже разобрала transform с учётом типа экрана и прислала
  готовую ориентацию. НЕ интерпретируй wl_output::transform повторно,
  если движок использует события SDL2. Сначала проверь в коде движка,
  обрабатывает ли он SDL_DISPLAYEVENT_ORIENTATION и как.
- В модифицированном под Аврору GLFW (см. «Сборка пакета», ветка
  3.4-wl-shell) поддержка ориентации есть — используй её:
    - enum GLFW_TRANSFORM_NORMAL / _90 / _180 / _270 (значения 0–3,
      совпадают с wl_output_transform) и FLIPPED-варианты (4–7);
    - glfwGetMonitorTransform(monitor) — текущий transform монитора;
    - событие GLFW_TRANSFORM_CHANGED через glfwSetMonitorCallback
      (приходит в том же колбэке, что GLFW_CONNECTED/GLFW_DISCONNECTED);
    - glfwSetWindowContentTransform(window, transform) — готовая
      обёртка над wl_surface_set_buffer_transform: выставляет buffer
      transform без ручной линковки wayland-client (используй её
      вместо сниппета из этапа 3 — он для SDL2).
  Если используется этот GLFW — НЕ интерпретируй wl_output::transform
  вручную, бери значения из GLFW API.
- Дополнительно проверь, как движок получает размер окна. Учти: при
  повороте события изменения размера (SDL_WINDOWEVENT_SIZE_CHANGED)
  НЕ приходят — см. подраздел «Размер окна и буфера при повороте».
  Обработчики resize движка нужно вызывать вручную при реальной
  смене размеров буфера.

## Сборка пакета

### Имя пакета и песочница
Пакет конечного приложения называется org.example.appname-1.0.0-3.aarch64.rpm,
где `org.example` — обратное доменное имя организации или разработчика,
`appname` — название приложения, `1.0.0` — версия (часть Version в spec-файле),
`3` — номер сборки (часть Release в spec-файле), `aarch64` — архитектура пакета.

На платформе Аврора пакет работает внутри песочницы и имеет следующие
ограничения:
- Все зависимости, которые собираются вместе с проектом, должны быть
  установлены вместе с пакетом в `/usr/share/org.example.appname/`, и далее,
  после сборки проекта, конечному бинарному файлу должен быть либо прописан
  rpath до этой папки, либо (проще) в секции `%install` spec-файла вызвать
  `patchelf` для добавления этого пути в пути поиска линковщика. Например,
  если собран проект mygame, установка выглядит так:
  ```
  install -m 0655 -D build/%{_arch}/mygame/mygame %{buildroot}%{_bindir}/%{name}
  patchelf --force-rpath --set-rpath %{_datadir}/%{name}/lib %{buildroot}%{_bindir}/%{name}
  ```
  По умолчанию patchelf вызывается в spec-файле, однако если в проекте
  собираются библиотеки, которые зависят друг от друга, их тоже стоит
  пропатчить, добавив правильный путь поиска линковки, по примеру выше.

### Структура каталога сборки
Во всех местах, где это предусмотрено системой сборки, собранные бинарные
артефакты, объектные файлы и сгенерированные промежуточные файлы должны
попадать в директорию `build` в корне репозитория. Внутри неё — папки
`aarch64` и `armv7hl`, в которых лежат отдельные папки для всех собранных
зависимостей. Например, если собирается библиотека `libfoo`, то собранная
под aarch64 библиотека и артефакты сборки (объектники, cmake-файлы и прочее)
лежат в `build/aarch64/libfoo/*`.

### Тулчейн AuroraSDK
Путь до утилиты **sfdk** берётся из `port_config.json` (поле `sfdk`).
Далее sfdk используется для работы с AuroraSDK.

#### Ограничение: только sfdk
Вся работа со сборочным окружением Авроры — ТОЛЬКО через утилиту sfdk
(путь из `port_config.json`). ЗАПРЕЩЕНО напрямую трогать сборочный
движок и его инфраструктуру: docker/VirtualBox-контейнеры и VM,
ssh в движок, known_hosts, конфиги движка и SDK. Любые проблемы с
движком решаем командами sfdk (`sfdk engine start/stop/status` и т.п.)
или эскалируем пользователю. Обычные инструменты командной строки
(cmake, ninja, git, компиляторы хоста) запускать можно.

#### Получение списка таргетов
  `sfdk engine exec sb2-config -l`
  Вывод содержит строки вида `AuroraOS-5.1.6.65-MB2-aarch64`, где
    - `5.1.6.65` — версия ОС
    - `aarch64` — архитектура таргета
  Также будут таргеты с суффиксом `.default` — это снапшоты, их НЕ
  используем при сборке: SDK автоматически создаёт снапшот из таргета
  и использует его.
  При получении списка таргетов выбираем 2 таргета с архитектурами armv7hl
  и aarch64, исходя из условия, что их версии одинаковы и >= 5.1.0.0
  (либо соответствуют полю `target` из `port_config.json`, если пользователь
  задал конкретную версию).
  Полученные таргеты используются в связке со sfdk для вызова команд сборки:
  ```
  sfdk -c target=<target_name> <command>
  ```
  где <target_name> — имя таргета, например `AuroraOS-5.1.6.65-MB2-aarch64`,
  а <command> — команда для таргета: `build-init`, `prepare`, `build`
  (описаны ниже).

#### Инициализация, подготовка и сборка
В рецептах ниже вместо <target_name> подставлять имя одного из таргетов.
По умолчанию отлаживать и тестировать сборку для архитектуры `aarch64`.
1. Перед началом сборки вызвать инициализацию:
   `sfdk -c target=<target_name> build-init`
   build-init можно вызвать один раз в репозитории, он создаёт конфигурацию
   для сборки; далее используются только шаги prepare и build.
2. Подготовка сборки `prepare`:
   `sfdk -c target=<target_name> prepare` — выполняется установка
   зависимостей `BuildRequires` из spec-файла в таргет, а также этап
   `%prep` из spec-файла.
3. Сборка RPM-пакета `build`:
   `sfdk -c target=<target_name> build` — выполняются все этапы из секции
   `%build`; после удачной сборки происходит упаковка в RPM.

### Структура репозитория
- `rpm/` — spec-файл, который используется тулчейном для сборки проекта
  под платформу.
- `icons/` — файлы иконок приложения. Их трогать не нужно, их установка
  прописана в spec-файле.
- `docs/` — дополнительные методички (`docs/GLES3_Render_Research_Plan.md`
  — методика этапа «Мобильный рендер», `docs/maliit_keyboard.md` —
  вызов экранной клавиатуры Maliit, `docs/mce_display_blanking.md` —
  запрет гашения экрана через MCE, `docs/imgui_launcher.md` —
  лаунчер на Dear ImGui, `docs/imgui-theme-spec.md` — тема
  оформления для него, `docs/touch_ui.md` — виртуальный геймпад).
- `examples/` — примеры кода для портирования (`examples/maliit/` —
  клиент Maliit на C и мост в SDL2, `examples/mce/` — модуль запрета
  гашения экрана на C, `examples/launcher/` — эталонный лаунчер на
  ImGui, `examples/imgui/` — Dear ImGui с фиксами под тач-ввод).

### Зависимости сборки

#### cmake
Если портируемый проект собирается с cmake, добавляем BuildRequires:
```
BuildRequires: ninja
BuildRequires: cmake
BuildRequires: extra-cmake-modules
```
и при вызове команды конфигурации cmake передаём путь до ninja
(специфика платформы), например:
```
cmake \
    -G Ninja \
    -DCMAKE_MAKE_PROGRAM=/usr/bin/ninja \
    <другие флаги сборки> \
    -S mygame \
    -B build/%{_arch}/mygame
```

#### SDL2 (с фиксами под ОС Аврора)
При сборке пакета использовать ТОЛЬКО эту версию SDL2 — в ней фиксы
под ОС Аврора (если проект требует SDL2):
- https://github.com/savegame/SDL
Репозиторий выкачивается как подмодуль в папку `libsdl`.

1. В spec-файле добавить следующие `BuildRequires`:
```
BuildRequires: pkgconfig(wayland-client)
BuildRequires: pkgconfig(wayland-cursor)
BuildRequires: pkgconfig(wayland-egl)
BuildRequires: pkgconfig(wayland-protocols)
BuildRequires: pkgconfig(wayland-scanner)
BuildRequires: pkgconfig(glesv2)
BuildRequires: pkgconfig(xkbcommon)
BuildRequires: pkgconfig(vulkan)
BuildRequires: pkgconfig(egl)
BuildRequires: pkgconfig(sdl2)
BuildRequires: pkgconfig(libpulse)
```
2. В секции `%build`, перед сборкой основного проекта, добавить скрипт:
```
cmake \
    -G Ninja \
    -DCMAKE_MAKE_PROGRAM=/usr/bin/ninja \
    -Bbuild/%{_arch}/libsdl \
    -DCMAKE_BUILD_TYPE=Release \
    -DSDL_PULSEAUDIO=ON \
    -DSDL_RPATH=OFF \
    -DSDL_AUDIO=ON \
    -DSDL_STATIC=OFF \
    -DSDL_WAYLAND=ON \
    -DSDL_X11=OFF \
    -DSDL_WAYLAND_LIBDECOR=OFF \
    libsdl

cmake --build build/%{_arch}/libsdl -j`nproc`
pushd build/%{_arch}/libsdl
rsync -avP include-config-release/SDL2/* include/SDL2/
rsync -avP *.so* lib/
popd
```
3. В `%install` добавить установку:
```
install -D -s build/%{_arch}/libsdl/libSDL2-2.0.so* -t %{buildroot}%{_datadir}/%{name}/lib
```

#### GLFW3 (с фиксами под ОС Аврора)
Использовать ТОЛЬКО эту версию GLFW3 — в ней фиксы под ОС Аврора
(если проект требует GLFW3):
- https://github.com/savegame/glfw (ветка `3.4-wl-shell` — в ней
  события ориентации дисплея и glfwSetWindowContentTransform)
Репозиторий выкачивается как подмодуль в папку `glfw3`.

1. В spec-файле добавить следующие `BuildRequires`:
```
BuildRequires: pkgconfig(wayland-client)
BuildRequires: pkgconfig(wayland-cursor)
BuildRequires: pkgconfig(wayland-egl)
BuildRequires: pkgconfig(wayland-protocols)
BuildRequires: pkgconfig(wayland-scanner)
BuildRequires: pkgconfig(glesv2)
BuildRequires: pkgconfig(xkbcommon)
BuildRequires: pkgconfig(vulkan)
BuildRequires: pkgconfig(egl)
```
2. В секции `%build`, перед сборкой основного проекта, добавить скрипт:
```
mkdir -p build/%{_arch}/glfw
cmake \
    -G Ninja \
    -DCMAKE_MAKE_PROGRAM=/usr/bin/ninja \
    -DGLFW_LIBRARY_TYPE=STATIC \
    -DCMAKE_BUILD_TYPE=Release \
    -DGLFW_BUILD_WAYLAND=ON \
    -DGLFW_BUILD_X11=OFF \
    -DGLFW_STANDALONE=OFF \
    -DGLFW_AURORAOS=ON \
    -DGLFW_BUILD_EXAMPLES=OFF \
    -DGLFW_BUILD_TESTS=OFF \
    -DGLFW_BUILD_DOCS=OFF \
    -DCMAKE_INSTALL_PREFIX=build/%{_arch}/glfw.install \
    -Bbuild/%{_arch}/glfw \
    -Sglfw3
cmake --build build/%{_arch}/glfw
cmake --install build/%{_arch}/glfw
```
glfw удобно собрать статикой, но можно и динамикой. Далее в приложении
нужно указать пути для линковки с glfw, например вызвать cmake через env:
```
env CMAKE_PREFIX_PATH=build/%{_arch}/glfw.install:$CMAKE_PREFIX_PATH \
cmake <флаги cmake>
```
или другим способом (исправить скрипты сборки проекта, если это доступно).

#### Прочие зависимости
Проекту могут потребоваться другие зависимости, кроме описанных здесь.
Действуем следующим образом:
- Если это SDL2 — берём модифицированную, описано выше.
- Если это библиотека (например ogg, vorbis, curl и т.п.) — найти
  репозиторий с ней, выгрузить как подмодуль нужной версии, добавить
  скрипты сборки в секцию `%build`, а установку делать в секции `%install`
  при помощи команды `install` в папку `/usr/share/%{name}/lib/`.
- Если это система сборки (waf) — сначала выгрузить и собрать эту утилиту,
  положить как подмодуль в папку `tools`.
- Если зависимость доступна в репозитории ОС Аврора — пробуем использовать
  её, если версия подходит (желательно подкрутить скрипты сборки, чтобы
  версия из репозитория подходила). Проверка доступности зависимости:
  выполняем команды zypper внутри снапшота нужного таргета (т.е. с суффиксом
  `.default`), например:
  ```
  sfdk engine exec sb2 -t AuroraOS-5.1.3.85-MB2-aarch64.default -R -m sdk-install zypper se scons
  ```
  Если нашли — добавляем в `BuildRequires`, причём желательно использовать
  имя pkgconfig-файла вместо названия пакета: так spec становится гибче
  и не зависит от версии таргета:
  ```
  BuildRequires: pkgconfig(openal)
  ```
  Если зависимость не предоставляет pkgconfig-файлов — пишем по названию
  пакета:
  ```
  BuildRequires: scons
  ```

#### Исключение добавленных зависимостей из валидации разрешённых библиотек
Если в spec попадают зависимости, которые устанавливаются в
`/usr/share/%{name}/lib`, их нужно прописать в spec-файле
(например, библиотеки libfoo.so.1 и libbar.so.1):
```
%define __requires_exclude ^libfoo.*\\.so.*|libbar\\.so.*$
```
Все библиотеки записываются в виде регулярного выражения для spec.

### Подпись пакета
После сборки первого RPM его нужно подписать ключами из SDK.
Подпись обязательна перед любой проверкой пакета: перед запуском
валидатора и перед установкой на устройство. Не подписываем пакет
ТОЛЬКО если пользователь явно попросил этого не делать.
- Ключи берём либо из SDK (папка `package-signing`: `regular_cert.pem`
  и `regular_key.pem`), либо скачиваем:
  https://developer.auroraos.ru/content-images/dev-documentation/regular_key.pem
  https://developer.auroraos.ru/content-images/dev-documentation/regular_cert.pem
  Кладём в корень проекта.
- Подписываем:
  ```
  sfdk engine exec sb2 -t <target_name>.default rpmsign-external sign -c /path/to/regular_cert.pem -k /path/to/regular_key.pem RPMS/org.example.appname-<version-release, может содержать git-хеш>.aarch64.rpm
  ```

### Валидация пакета (rpm-validator)
Далее пакет прогоняется через валидатор — так узнаём, есть ли
в зависимостях библиотеки, с которыми нельзя линковаться напрямую
(например, OpenAL):
```
sfdk engine exec sb2 -t <target_name>.default rpm-validator -p regular org.example.appname-<version-release, может содержать git-хеш>.aarch64.rpm
```
Если валидатор пишет, что библиотека (например, libopenal) не разрешена
как зависимость линковки — добавляем копирование этой библиотеки
из таргета в наш пакет, в `/usr/share/org.example.appname/lib`:
```
install -D %{_libdir}/libopenal.so.1* -t %{buildroot}%{_datadir}/%{name}/lib/
```
и, как описано в правиле выше (см. «Исключение добавленных зависимостей
из валидации разрешённых библиотек»), добавляем её имя
в `__requires_exclude`.

## Файл статуса port_status.md

Агент обязан вести файл `port_status.md` в корне репозитория и обновлять
его после каждого этапа. Файл — единственный источник правды о состоянии
портирования: новый агент в новой сессии должен по нему однозначно
понять, что сделано и что дальше. Структура файла:

```
# Статус портирования <имя проекта>

## Текущее состояние
Текущий этап, режим работы (автоматический/ручной), дата обновления.

## Результаты анализа
Найденное при разведке: графический API, способ вызова swap, куда
рендерится сцена, как движок получает размер экрана, пути вывода
графики, собственный API render target, опасные места.

## План портирования
Конкретный план для этого проекта: какие файлы будут меняться, какой
дефайн выбран, как интегрируется FBO-модуль.

## Чеклист
- [ ] Этап 0 — исследование проекта
- [ ] Этап «Мобильный рендер» (условный — по решению пользователя)
- [ ] Этап 1 — сборка под Аврору
- [ ] Этап «Гашение экрана (MCE)» (условный, рекомендуемый — по решению пользователя)
- [ ] Этап «Лаунчер (imgui)» (условный — если нет свободно распространяемых ресурсов)
- [ ] Этап 2 — интеграция FBO
- [ ] Этап 3 — поворот и ресайз контента
- [ ] Этап 4 — трансформация ввода
- [ ] Этап «Тач-UI (виртуальный геймпад)» (условный — если в игре нет своего тач-UI)
- [ ] Этап 5 — тестирование на устройстве
- [ ] Этап 6 — финальный RPM
- [ ] Этап «Встроенная клавиатура» (условный — по решению пользователя)
(пункты дополняются подзадачами по мере работы)

## Ошибки и замечания
Ошибки, найденные пользователем при прогоне и тестировании, с описанием
симптомов, гипотез и статуса (открыта / в работе / закрыта).
```

Правила ведения:
- Обновляй файл после каждого завершённого шага, а не в конце сессии.
- В чеклисте отмечай выполненное сразу после проверки критерия этапа.
- Ошибки не удалять — закрытые помечать как закрытые с кратким
  описанием решения.
