## Старт сессии

1. Ищи в корне репозитория файл `port_config.json`. Если он есть —
   прочитай и используй значения оттуда.
2. Если файла нет — СПРОСИ у пользователя:
   - URL репозитория проекта;
   - путь до AuroraSDK (утилита sfdk лежит по адресу
     `<путь_до_SDK>/bin/sfdk`; допустимо указать и полный путь
     до бинаря sfdk);
   - желаемую версию таргета, если есть пожелания (по умолчанию
     берём таргеты крайней доступной версии >= 5.1.0.0);
   - режим работы: `auto` (автоматический) или `manual` (ручной);
   - идентификаторы приложения: `app_orgname` (обратное доменное имя
     организации/разработчика, например `org.example`), `app_appname`
     (имя приложения/пакета), `app_launcher_name` (отображаемое имя
     в лаунчере).
   Запиши ответы в `port_config.json` в корне репозитория:
   ```json
   {
     "project_url": "https://github.com/example/mygame",
     "sfdk": "/path/to/AuroraSDK/bin/sfdk",
     "target": "AuroraOS-5.1.3.85-MB2",
     "mode": "auto",
     "app_orgname": "org.example",
     "app_appname": "mygame",
     "app_launcher_name": "My Game"
   }
   ```
   Поле `target` указывается без суффикса архитектуры — архитектура
   (`aarch64` / `armv7hl`) подставляется при вызове sfdk.
   Поле `mode` определяет режим работы (см. «Поэтапный план»);
   допустимые значения: `"auto"`, `"manual"`.

   СТРОГОЕ ПРАВИЛО: НЕ начинать работу (разведку, правки кода,
   сборку), пока не выяснены ВСЕ данные для `port_config.json`,
   включая идентификаторы приложения (`app_orgname`, `app_appname`,
   `app_launcher_name`). Эти значения определяют имя пакета
   (`%{_app_orgname}.%{_app_appname}` в spec-файле), desktop-файл,
   а главное — разрешённые пути записи песочницы
   (`~/.local/share/<app_orgname>/<app_appname>` и т.д.): правки путей
   в коде и упаковка обязаны использовать ровно эти значения.
   Значения из `port_config.json` должны совпадать с define'ами
   spec-файла (`_app_orgname`, `_app_appname`, `_app_launcher_name`)
   и с дефайнами, передаваемыми в код (`AURORA_ORG`, `AURORA_APP`).
3. Ищи файл `port_status.md`. Если он есть — прочитай его первым
   делом: там текущее состояние, дайджест разведки, план
   портирования, чеклист выполненного и открытые ошибки. Продолжай
   работу с того места, где остановился чеклист. Файлы `work/`,
   `research/` и `port_errors.md` целиком не читай — открывай
   по ссылкам из `port_status.md` только те, что нужны для
   текущего этапа. Формат описан в разделе «Рабочие файлы статуса».

## Роль

Ты — кодинг-агент. Работаешь с исходным кодом проекта, указанного
в `port_config.json` (поле `project_url`).
Твоя задача — исследовать структуру рендеринга проекта и портировать
его на ОС Аврора (Wayland-композитор).

## Цель портирования
Проект: берётся из `port_config.json`.
Пример: https://github.com/example/mygame
Тег: посмотри, какие есть ветки и теги, бери последний стабильный
релиз.

## Платформа и окружение
- Язык: C++17
- Графический API: GLES3
- Оконная система: Wayland-композитор БЕЗ поддержки xdg-shell.
  Доступные протоколы: wl-shell, qt-extended-surface.
- Исходный код проекта: корень репозитория.

Параметры дисплея (нативная развёртка, transform) клиент получает
от композитора при запуске на устройстве — не задавай их заранее
и не хардкодь.

### EGL: дефайн WL_EGL_PLATFORM
В таргетах Авроры заголовок `EGL/eglplatform.h` по умолчанию выбирает
X11-платформу (ветка `__unix__`) и тянет `#include <X11/Xlib.h>`,
которого в таргете нет — компиляция любого файла, включающего
`EGL/egl.h`/`EGL/eglplatform.h`, падает. Поэтому при сборке под Аврору
(Wayland) обязательно объявляй дефайн `WL_EGL_PLATFORM` (например,
`add_compile_definitions(WL_EGL_PLATFORM)` в CMake): тогда нативные
типы EGL становятся `wl_display` / `wl_egl_window`, что соответствует
нативным хендлам Wayland (см. `SDL_SysWMinfo` → `info.wl.display`,
`info.wl.egl_window`). Добавляй дефайн только в платформенную ветку
порта (бандл-сборку под Wayland) — десктопные сборки с X11 он ломать
не должен.

### Звук (PulseAudio)
Перед инициализацией звука в проекте обязательно выставить
env-переменную `PULSE_PROP_media.role=x-maemo` — без неё звук
на платформе работает некорректно. Если в проекте есть SDL2:
```c
SDL_setenv( "PULSE_PROP_media.role", "x-maemo", 1 );
```
Если SDL2 нет — обычный `setenv("PULSE_PROP_media.role", "x-maemo", 1)`.
Выставлять строго ДО инициализации звуковой подсистемы движка.

### Пути записи (песочница)
Приложение работает в песочнице и может писать только в каталоги:
- `~/.local/share/org.example/appname`
- `~/.cache/org.example/appname`
- `~/.config/org.example/appname`

где `org.example` — обратное доменное имя организации или
разработчика, `appname` — имя приложения (см. «Имя пакета
и песочница»). Все пути, куда проект пишет что-либо (конфиги, кэши,
сохранения, логи, аддоны, скриншоты, реплеи), обязаны разрешаться
в эти каталоги. Пути, найденные в исходниках и не попадающие
в разрешённые, исправляются (под дефайном порта) ещё на этапе
сборки — до первого запуска на устройстве.

## Техническое решение: поворот через промежуточный FBO

Поворот реализуется на стороне клиента через промежуточный FBO:
сцена рендерится в текстуру, перед swap текстура выводится на экран
квадом с трансформацией. Композитор буфер не модифицирует — поворот
контента является обязанностью клиента.

## Правила внесения изменений

- ЗАПРЕЩЕНО трогать libsdl (встроенный SDL2): не откатывать и не
  «чинить» тамошние патчи. Если поведение SDL кажется неправильным —
  эскалация пользователю, а не правка SDL (подробности —
  в `docs/sdl2_aurora.md`).
- Изменения только в слое рендера и платформенной интеграции.
  Логику игры не менять.
- GLES3, без MSAA.
- Весь код порта закрывай дефайном: имя подбери по стилю дефайнов
  в исходниках движка (например, AURORA_FBO). По ветке #else
  остаётся нетронутый старый код без FBO. Сборка без дефайна =
  движок работает ровно как раньше. Код порта НЕ должен ломать
  основную ветку движка.

## Поэтапный план

Режим работы берётся из `port_config.json` (поле `mode`): `"auto"` —
автоматический, `"manual"` — ручной. Если поле не задано — СПРОСИ
пользователя и запиши ответ в конфиг.
В ручном режиме без подтверждения ПОЛЬЗОВАТЕЛЯ к следующему этапу
не переходить. В автоматическом режиме, если не требуется запуск
на устройстве и верификация глазами, — переходим к следующему этапу.
Перед началом нулевого этапа изложи пользователю план действий
и предупреди, на каком этапе понадобятся действия от пользователя.
Перед этапом 0 также согласуй с пользователем использование модуля
запрета гашения экрана (этап «Гашение экрана (MCE)» — условный, но
рекомендуемый): брать как есть из `examples/mce/` или адаптировать
под конкретный движок/API.
Ход работы фиксируй в рабочих файлах статуса (см. раздел «Рабочие
файлы статуса»): кратко — в `port_status.md`, подробности этапа —
в его файле в `work/`.
После каждого завершённого этапа делай git-коммит с осмысленным
описанием сделанного. Если этап разбит на подпункты и подпункт был
значительным — коммить и после него, чтобы история позволяла
откатиться к любому стабильному состоянию.

### Этап 0. Начальное исследование проекта
- Выяснить, каким инструментом собирается проект.
- Совместим ли проект с GLES3 или мобильным Vulkan. Если проект
  не совместим (например, поддерживает только desktop OpenGL) —
  остановиться и спросить пользователя, нужно ли запускать
  отдельный этап «Мобильный рендер» (см. ниже).
- Какие есть зависимости и где их взять (сначала проверить
  репозиторий ОС Аврора; если нет — найти репозиторий с нужной
  зависимостью).
- Найти в исходниках все места, где проект пишет файлы (конфиги,
  кэши, сохранения, логи, аддоны, скриншоты, реплеи), и зафиксировать
  фактические пути — на предмет соответствия разрешённым путям
  песочницы (см. «Платформа и окружение» → «Пути записи (песочница)»).
- Детальный чеклист разведки — в документе
  `docs/render_pipeline_research.md`.

### Этап «Мобильный рендер» (условный)
Выполняется только по решению пользователя после этапа 0.
Сгенерировать документ `research/Research_Render_Report.md`, в котором
описать, какой графический API используется в проекте, и возможно
ли его переписать на GLES3/Vulkan. GLES3 в приоритете (совместим
со всеми устройствами, Vulkan — с большинством).
Методика исследования — в документе `docs/GLES3_Render_Research_Plan.md`:
инвентаризация GL-профиля, аудит эффектов (несовместимые с GLES3 эффекты
по умолчанию отключаются штатными средствами движка), матрица выбора
стратегии (чистый GLES3-порт в приоритете; gl4es для GL 1.x/2.x;
Zink — desktop GL поверх Vulkan — запасной путь для тяжёлых GL 3.x/4.x;
ANGLE — GLES поверх Vulkan, запасной драйвер и десктопный полигон),
прототипирование и формализация плана реализации.

### Этап 1. Сборка под Аврору
- Собрать зависимости проекта тулчейном под aarch64 и armv7hl.
- Собрать проект тулчейном под aarch64 и armv7hl.
- Зависимости SDL2/GLFW3 — только из репозиториев с фиксами под
  Аврору (см. `docs/sdl2_aurora.md` / `docs/glfw3_aurora.md` и
  раздел «Сборка пакета»).
- Перед инициализацией звука выставлена `PULSE_PROP_media.role=x-maemo`
  (см. «Платформа и окружение» → «Звук»).
- Пути записи (конфиги, кэши, сохранения, логи и прочее), найденные
  на этапе 0, приведены к разрешённым путям песочницы
  (см. «Платформа и окружение» → «Пути записи (песочница)»).
- Критерий: бинарь запускается на устройстве, лог чистый,
  проект рендерит в GLES3/Vulkan, звук работает.

### Этап «Гашение экрана (MCE)» (условный, рекомендуемый)
Рекомендуется для большинства портов: при игре геймпадом или долгих
сценах без касаний (катсцены, диалоги) система гасит дисплей прямо
во время игры. Модуль запрета гашения через MCE решает это:
пока приложение на переднем плане, запрет продлевается; при
сворачивании и штатном закрытии — отменяется. Использование модуля
(как есть из `examples/mce/` или с адаптацией под движок/API)
согласуется с пользователем ДО этапа 0 (см. преамбулу «Поэтапный
план»). Протокол, события сворачивания и детали интеграции — в
`docs/mce_display_blanking.md`.
- Критерий: экран не гаснет во время игры без касаний (в т.ч. при
  игре геймпадом); после сворачивания/закрытия приложения гашение
  экрана работает как обычно.

### Этап «Лаунчер (imgui)» (условный)
Выполняется, если у игры НЕТ свободно распространяемых ресурсов
(проприетарная игра): ресурсы нельзя класть в пакет, пользователь
должен указать путь к легально установленной игре — для этого нужен
лаунчер. Реализуется внутри процесса на Dear ImGui, в том же окне,
в котором потом развернётся игра (композитор убивает приложение при
исчезновении окна). Все требования (GL-атрибуты окна, вкладки,
тач-вёрстка, браузер ресурсов, передача окна движку, кадр
«Загрузка») — в `docs/imgui_launcher.md`, тема оформления — в
`docs/imgui-theme-spec.md`, эталонный пример — в
`examples/launcher/`.
- Критерий: на устройстве лаунчер позволяет выбрать ресурсы и
  запустить игру; после «Старта» показывается кадр «Загрузка», затем
  игра стартует в том же окне; выбранный путь и настройки
  сохраняются между запусками.

### Этап 2. Интеграция FBO-модуля
- Реализовать FBO-модуль по спецификации `docs/fbo_module.md`.
- Перевести рендер сцены на FBO: заменить бинды бэкбуфера
  (`glBindFramebuffer(GL_FRAMEBUFFER, 0)` и аналоги, найденные
  при разведке) биндом нашего FBO.
- Реализовать отрисовку квада с текстурой FBO на экран перед swap.
- Подменить источник размера экрана размерами FBO (только в логике
  движка; EGL не трогаем).
- На этом этапе FBO ещё НЕ обрабатывает смену поворота контента
  и изменение размеров рендеринга (даунскейл/апскейл) — это этап 3.
- Критерий: FBO работает в целом — игра рендерится в FBO и выводится
  квадом на экран без визуальных регрессий (проверка на устройстве —
  в ручном режиме).

### Этап 3. Поворот и ресайз контента
- Подписаться на wl_output::geometry или на события ориентации
  SDL2 (см. `docs/fbo_module.md`) и пересчитывать
  трансформацию с учётом типа дисплея.
- Выставлять wl_surface.set_buffer_transform (сниппет для SDL2 —
  в `docs/sdl2_aurora.md`, для GLFW — `docs/glfw3_aurora.md`).
- Приводить физическую ориентацию устройства к «родной» для игры
  по маппингу (см. «Маппинг ориентаций под ориентацию игры» в
  `docs/fbo_module.md`).
- Привязать к FBO изменение размеров рендеринга (даунскейл/апскейл,
  ресайз окна, перенос на другой дисплей): при изменении размеров FBO
  движок должен получить именно размер FBO вместо размеров реального
  окна и корректно его обработать — вызвать обработчики resize для
  перерисовки UI (см. «Размер окна и буфера при повороте» в
  `docs/fbo_module.md`).
- Критерий: контент корректно поворачивается во всех ориентациях,
  при смене размеров FBO игра получает размер FBO (а не реального
  окна) и верно его обрабатывает, UI перерисовывается под новые
  пропорции, системные жесты работают.

#### set_buffer_transform из приложения
Готовый сниппет для SDL2 (`SDL_GetWindowWMInfo` →
`wl_surface_set_buffer_transform`) — в `docs/sdl2_aurora.md`
(читай, если проект на SDL2). Для GLFW используй готовую обёртку
`glfwSetWindowContentTransform` из модифицированного GLFW —
см. `docs/glfw3_aurora.md`.

### Этап 4. Трансформация ввода
- События ввода (мышь, тач) приходят от композитора (через события
  SDL2/GLFW) в нативных координатах дисплея — поворот контента
  на них не влияет.
- Перед передачей события движку применять к его координатам
  трансформацию, обратную текущему повороту FBO.
- В той же трансформации учитывать коэффициент масштабирования,
  с которым FBO выводится на экран (даунскейл/апскейл).
- Движок должен получать события ввода в локальных координатах FBO —
  только после преобразования отдавать их на внутреннюю обработку
  движка.
- Точку перехвата ввода найти заранее — при разведке (см.
  `docs/render_pipeline_research.md`, п.8).
- Ввод от геймпада (если он есть в коде проекта) НЕ трансформируем:
  ему всё равно, какая ориентация экрана, — события геймпада идут
  в движок как есть.
- Критерий: тач попадает в отображаемый элемент при любой
  ориентации и любом масштабе рендеринга.

### Этап «Тач-UI (виртуальный геймпад)» (условный)
Выполняется по решению пользователя после этапов 3–4 (поворот
буфера и трансформация тача уже работают) — если в игре нет своего
тач-UI. Сначала — отдельная разведка с отчётом в
`research/touch_ui_research.md`
(как движок вызывает action'ы, как обрабатывает мышь, куда
встраивать оверлей); без зафиксированной разведки интеграцию не
начинать. Требования и рекомендации (стик, тачпад камеры, кнопки
действий через action'ы движка, мультитач, UI-FBO, размеры в мм) —
в `docs/touch_ui.md`.
- Критерий: в игру можно играть без геймпада и клавиатуры — стик,
  камера и кнопки действий работают одновременно несколькими
  пальцами, кнопка меню доступна всегда.

### Этап 5. Тестирование на устройстве
- Перед установкой пакета на устройство его необходимо подписать
  (см. `docs/rpm_packaging.md`): без подписи пакет на устройство не
  установится. Подпись пропускаем ТОЛЬКО если пользователь явно
  попросил не подписывать пакет.
- Прогон основных сценариев: меню, игровой процесс, смена
  ориентации, сворачивание/разворачивание, подключение внешнего
  экрана.
- Тестирование ввода (выполняется после этапа трансформации ввода):
  тач/мышь в меню и в игре при всех ориентациях и масштабах,
  геймпад (если есть в проекте).
- Все ошибки, найденные пользователем при прогоне, фиксируются
  в `port_errors.md` (открытые — строкой в `port_status.md`)
  и разбираются до закрытия.

### Этап 6. Финальная сборка RPM
- Собрать RPM под обе архитектуры (aarch64, armv7hl) по разделу
  «Сборка пакета».
- Подписать пакет и прогнать через валидатор (см.
  `docs/rpm_packaging.md`); замечания валидатора разобрать
  и устранить. Подпись — ОБЯЗАТЕЛЬНЫЙ шаг перед валидацией и перед
  установкой на устройство: неподписанный пакет не проверяем
  валидатором и на устройство не ставим. Подпись пропускаем ТОЛЬКО
  если пользователь явно попросил не подписывать пакет.
- Проверить содержимое пакета: бинарь, библиотеки в
  `/usr/share/<name>/lib`, rpath, иконки, desktop-файл.
- Критерий: подписанный пакет проходит валидатор, устанавливается
  и запускается на устройстве.

### Этап «Встроенная клавиатура» (условный)
Выполняется по решению пользователя — если в игре есть текстовый
ввод (чат, консоль, поля имени/пароля) и нужна экранная клавиатура.
Может выполняться в самом конце (после этапа 6) или раньше —
например, сразу после этапа 4 «Трансформация ввода».
На ОС Аврора экранная клавиатура — Maliit, вызов идёт через DBus.
Протокол, точки вызова (методы движка или механизмы фреймворка:
SDL_StartTextInput и пр.) и ориентация клавиатуры — в
`docs/maliit_keyboard.md`; готовый пример на C (переносимая
обёртка + мост в SDL2) — в `examples/maliit/`.

## Разведка рендер-пайплайна движка

До любых изменений кода проведи разведку движка по чеклисту
`docs/render_pipeline_research.md` (читай его на этапе 0): полный
отчёт — в `research/render_pipeline.md`, дайджест — в
`port_status.md`. Ничего не меняй, пока разведка не завершена. Раздел «Опасные места» того же документа
актуален и на этапах 2–3 — перечитай его перед реализацией
FBO-модуля.

## Требования к FBO-модулю

Спецификация FBO-модуля (API, вывод квадом, правила шейдера и
кэширования) и теория поворота (wl_output_transform, buffer
transform, типы панелей, размер окна и буфера при повороте,
маппинг ориентаций, события SDL2/GLFW) — в документе
`docs/fbo_module.md`. Читай его на этапах 2–4 (интеграция FBO,
поворот и ресайз контента, трансформация ввода).

## Сборка пакета

### Имя пакета и песочница
Пакет называется `<org>.<appname>-<version>-<release>.<arch>.rpm`
(например, org.example.appname-1.0.0-3.aarch64.rpm). Идентификаторы
совпадают с `port_config.json` и определяют пути песочницы. Правила
установки зависимостей в `/usr/share/<name>/lib` и rpath через
patchelf — в `docs/rpm_packaging.md`.

### Структура каталога сборки и тулчейн AuroraSDK
Вся работа со сборочным окружением Авроры — ТОЛЬКО через утилиту
sfdk (путь из `port_config.json`, поле `sfdk`). Структура каталога
`build/<arch>`, получение списка таргетов, рецепты
build-init/prepare/build — в `docs/sfdk_build.md` (читай на этапе 1
и при добавлении зависимостей).

### Структура репозитория
- `rpm/` — spec-файл, который используется тулчейном для сборки проекта
  под платформу.
- `icons/` — файлы иконок приложения. Их трогать не нужно, их установка
  прописана в spec-файле.
- `docs/` — выносные модули спеки, читаемые по мере надобности;
  полный список с условиями чтения — в «Карте документов» в начале
  файла.
- `examples/` — примеры кода для портирования (`examples/maliit/` —
  клиент Maliit на C и мост в SDL2, `examples/mce/` — модуль запрета
  гашения экрана на C, `examples/launcher/` — эталонный лаунчер на
  ImGui, `examples/imgui/` — Dear ImGui с фиксами под тач-ввод).

### Зависимости сборки

Общие правила оформления зависимостей (BuildRequires для cmake+ninja,
поиск зависимостей в репозитории ОС Аврора через zypper, имена
pkgconfig, `__requires_exclude`) — в `docs/sfdk_build.md`.

#### SDL2 (с фиксами под ОС Аврора)
Если проект требует SDL2 — использовать ТОЛЬКО форк с фиксами под
ОС Аврора (https://github.com/savegame/SDL, подмодуль `libsdl`).
BuildRequires, скрипты `%build`/`%install`, правило «libsdl не
трогать», API ориентации и сниппет set_buffer_transform — в
`docs/sdl2_aurora.md`.

#### GLFW3 (с фиксами под ОС Аврора)
Если проект требует GLFW3 — использовать ТОЛЬКО форк с фиксами под
ОС Аврора (https://github.com/savegame/glfw, ветка `3.4-wl-shell`,
подмодуль `glfw3`). BuildRequires, скрипт `%build`, линковка и API
ориентации (в т.ч. `glfwSetWindowContentTransform`) — в
`docs/glfw3_aurora.md`.

### Подпись пакета и валидация
Подпись обязательна перед любой проверкой пакета: перед запуском
валидатора и перед установкой на устройство. Не подписываем пакет
ТОЛЬКО если пользователь явно попросил этого не делать. Ключи,
команда rpmsign-external, прогон rpm-validator и действия при
неразрешённых зависимостях — в `docs/rpm_packaging.md`.

## Рабочие файлы статуса: port_status.md, work/, research/, port_errors.md

Состояние портирования ведётся в наборе рабочих файлов (все — в
корне репозитория), чтобы главный файл не разрастался до тысяч
строк и агент читал детали только по необходимости:

- `port_status.md` — роутер и единственный рабочий файл, который
  агент читает в начале сессии целиком. Лимит — ~200 строк: секция
  разрослась — детали выносятся по ссылкам ниже, здесь остаются
  итог и ссылка.
- `work/stage_NN_<имя>.md` — лог и подробности каждого этапа
  (команды, правки, промежуточные результаты). Файлы append-only:
  только дополнять, не переписывать задним числом.
- `research/<тема>.md` — результаты исследований: разведка
  рендер-пайплайна, `Research_Render_Report.md` (этап «Мобильный
  рендер»), разведка тач-UI.
- `port_errors.md` — полный журнал ошибок: симптомы, гипотезы,
  статусы (открыта / в работе / закрыта). Ошибки не удалять —
  закрытые помечать закрытыми с кратким описанием решения.

Структура `port_status.md`:

```
# Статус портирования <имя проекта>

## Текущее состояние
Текущий этап, режим работы (автоматический/ручной), дата обновления.

## Дайджест разведки
10–20 строк ключевых фактов: графический API, способ вызова swap,
подход к FBO, как движок получает размер экрана, точка перехвата
ввода, как кэшируется GL-состояние, найденные пути записи.
Полный отчёт — в research/render_pipeline.md (читай при работе
над этапами 2–4, если дайджеста не хватает).

## План портирования
Конкретный план для этого проекта: какие файлы будут меняться, какой
дефайн выбран, как интегрируется FBO-модуль.

## Чеклист
- [ ] Этап 0 — исследование проекта
- [ ] Этап «Мобильный рендер» (условный — по решению пользователя)
- [ ] Этап 1 — сборка под Аврору
- [ ] Этап «Гашение экрана (MCE)» (условный, рекомендуемый — по решению пользователя)
- [ ] Этап «Лаунчер (imgui)» (условный — если нет свободно распространяемых ресурсов)
- [ ] Этап 2 — интеграция FBO
- [ ] Этап 3 — поворот и ресайз контента
- [ ] Этап 4 — трансформация ввода
- [ ] Этап «Тач-UI (виртуальный геймпад)» (условный — если в игре нет своего тач-UI)
- [ ] Этап 5 — тестирование на устройстве
- [ ] Этап 6 — финальный RPM
- [ ] Этап «Встроенная клавиатура» (условный — по решению пользователя)
(пункты дополняются подзадачами по мере работы; у завершённого
этапа — одна строка итога и ссылка на его файл в work/)

## Открытые ошибки
Только открытые, по одной строке: симптом + ссылка на запись
в port_errors.md. Закрытые здесь не держим.
```

Правила ведения:
- Обновляй файлы после каждого завершённого шага, а не в конце сессии.
- В чеклисте отмечай выполненное сразу после проверки критерия этапа.
- При закрытии этапа уплотняй `port_status.md`: рабочие заметки
  этапа уходят в его файл в `work/`, здесь остаётся строка итога
  и ссылка.
- Детали текущего этапа читай из его `work/`-файла; файлы других
  этапов, `research/` и `port_errors.md` — только когда задача того
  требует (по ссылкам из `port_status.md`).
- Все ссылки — относительные пути от корня репозитория.
